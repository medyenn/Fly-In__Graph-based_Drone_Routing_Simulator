PHASE 1

Foundations & Theory

The vocabulary and mental models everything else depends on.

The mental model

You're an air-traffic controller for a drone fleet. A map of zones (parking spots) linked by connections (corridors). All drones start in one start_hub, all must reach one end_hub. Time moves in discrete turns; every active drone moves or waits each turn. Score = total turns until the last drone arrives. Fewer is better.

Why not just "shortest path"?

One drone → shortest path (Dijkstra) is enough. Many drones sharing capacity-limited zones/connections at the same time → you also need a scheduler that resolves who moves this turn without breaking capacity rules. That split (pathfinding vs. scheduling) is the backbone of the whole architecture.

Vocabulary

TermMeaning
Zone / HubA node. Name, coordinates, type, color, occupancy limit.
start_hub / end_hubThe unique origin / destination zone. Unlimited occupancy, always.
ConnectionA bidirectional edge between two zones, with its own capacity.
TurnOne discrete simultaneous time-step for the whole fleet.
ConflictTwo+ drones' intended moves would exceed a capacity rule.

Zone types & movement cost

TypeCost to enterRule
normal1 turnDefault.
priority1 turnSame cost as normal — but should be preferred when routes tie. A hint, not a discount.
restricted2 turnsOnce a drone departs toward it, it's committed: must arrive exactly next turn, can't idle mid-corridor.
blocked—Never enterable. Never part of a valid path.

Two independent capacity systems

  • Zone capacity — max_drones (default 1). Unlimited on start/end hubs.
  • Connection capacity — max_link_capacity (default 1). Limits simultaneous transits.
Key subtlety

Departures free up space within the same turn. Evaluate a turn as: process all departures first, then check capacity for arrivals — not against a stale "before this turn" snapshot.

Why this is (light) Multi-Agent Path Finding

  • Think in (resource, turn) pairs, not just "is X occupied" — capacity is per time-slot.
  • Reserve before you commit — before a drone departs (especially for a 2-turn restricted move), confirm the destination slot will be free on arrival turn.
  • Optimal MAPF is NP-hard and unnecessary here. A simple greedy strategy — best known path per drone, move when the next step is free, wait otherwise, prefer priority zones on ties — clears every mandatory requirement and most benchmarks.

Minimum algorithmic toolbox

ToolUsed for
BFS / Dijkstra (self-written)Cheapest route per drone, treating zone-type cost as the cost of entering that node.
Greedy turn resolutionPer turn, decide which proposed moves are actually legal.
Reservation tableDict keyed by (resource, turn) to prevent double-booking, esp. for restricted-zone transits.
Tie-break heuristicPrefer paths touching more priority zones when costs are equal.

No external graph library (forbidden anyway), no A*, no ILP solver — all of this is a few dozen lines each.

PHASE 2

Scope & Specification

Every subject rule turned into a testable checklist. This is your "definition of done."

File-format & parsing checklist

Must all be true
  • Line 1 = nb_drones: <positive int>; program supports any count.
  • Exactly one start_hub, exactly one end_hub.
  • Zone names unique; no dashes or spaces in names.
  • Connections reference only already-defined zones; a-b ≡ b-a (duplicate = error).
  • zone= ∈ {normal, blocked, restricted, priority} or it's a parse error.
  • max_drones / max_link_capacity must be positive ints when present; ignored (not an error) if written on start/end hub.
  • # comment lines and metadata in any key order are supported.
  • Any malformed line → clean error naming the line number and reason, program stops (no crash traceback).

Simulation-rule checklist

Must all be true
  • Zone occupancy respected every turn (default 1, or max_drones); start/end hubs unlimited.
  • Connection capacity respected (default 1, or max_link_capacity).
  • Departures free capacity within the same turn before arrivals are checked.
  • Restricted-zone moves are atomic 2-turn commitments — no mid-corridor waiting, no cancelling.
  • Blocked zones are never entered by any produced path.
  • Drones may move simultaneously, wait, or (for restricted) be mid-transit.
  • A drone that reaches end_hub is delivered and no longer tracked/scheduled.
  • Simulation stops exactly when all drones have arrived.

Output-format checklist

  • One line per turn.
  • Space-separated moves per line, format D<ID>-<zone> (arrival) or D<ID>-<connection> (in-flight toward a restricted zone).
  • Stationary drones omitted from that turn's line.
D1-roof1 D2-corridorA
D1-roof2 D2-tunnelB
D1-goal D2-goal

Non-functional checklist

  • Fully OOP, no external graph library, flake8 + mypy clean, typed, docstringed.
  • Visual feedback: colored terminal output and/or a graphical view.
  • Makefile targets: install, run, debug, clean, lint (lint-strict optional).
  • README.md: italic 42-attribution first line, Description, Instructions, Resources (incl. AI-usage disclosure), algorithm explanation, visualization documentation.

Scoring & benchmarks (your target, not a hard gate)

TierTarget turnsSample maps
Easy< 10Linear (2 drones, ≤6) · Simple fork (4, ≤8) · Basic capacity (4, ≤6)
Medium10–30Dead-end trap (5, ≤12) · Circular loop (6, ≤15) · Priority puzzle (5, ≤12)
Hard< 60Maze nightmare (8, ≤30) · Capacity hell (12, ≤35) · Ultimate challenge (15, ≤45)
Bonus — ChallengeroptionalImpossible Dream (25 drones), beat 45 turns

Primary score = total turns. Ties may be broken on secondary metrics (drones/turn, avg turns/drone, visualization quality) — worth logging even though not mandatory to compute.

PHASE 3

Architecture & Class Map

The simplest class set that cleanly covers every responsibility above — nothing more.

File layout

fly_in/
├── main.py            # entry point → FlyInApp
├── parser.py          # MapParser
├── domain.py          # Zone, Connection, Drone, Graph
├── pathfinder.py       # PathFinder
├── simulator.py        # Simulator
├── visualizer.py        # Visualizer
├── Makefile
├── README.md
└── maps/                # your own test maps (phase 10)

One module per class family. Small enough to navigate by memory, large enough to keep responsibilities separate — exactly what an evaluator expects from "fully OOP."

Dependency direction (who calls whom)

MapParser→ Graph (+Zone/Connection/Drone)→ PathFinder→ Simulator→ Visualizer

Data flows strictly left→right. FlyInApp (in main.py) is the only thing that knows about all of them — every other class only knows its immediate neighbor's output type. This is what keeps each class independently explainable at defense.

Class responsibility table

ClassSingle responsibility
ZoneRepresent one zone and its live occupancy.
ConnectionRepresent one edge and its live traversal load.
DroneRepresent one agent's identity, position and assigned path.
GraphOwn all zones/connections; answer adjacency queries.
MapParserTurn file text into a validated Graph + drone count.
PathFinderCompute a cheapest, priority-aware route for one drone.
SimulatorRun the turn loop; resolve capacity conflicts; produce the log.
VisualizerRender turns as colored terminal (and/or graphical) output.
FlyInAppWire everything together; the CLI entry point.

Nine classes total. That's the whole architecture — deliberately no more. Full attribute/method breakdown for each is in Phases 4–8.

Why exactly this split, and not more/fewer classes

Each class maps to a distinct question the project asks: "what does the text file mean?" (Parser) → "what does the network look like?" (Graph/Zone/Connection) → "where should one drone go?" (PathFinder) → "who actually moves this turn?" (Simulator) → "how do I show that to a human?" (Visualizer). Merging any two would mix unrelated questions into one class; splitting further would create classes with nothing meaningful of their own to own.

PHASE 4

Parser Module

Turn raw text into a validated Graph. Every rule from Phase 2's parsing checklist becomes one method here.

class MapParser

Attributes

  • filepath — path to the map file.
  • graph — the Graph being built.
  • nb_drones — parsed drone count.
  • line_number — tracked for error messages.

Methods

  • parse() — orchestrates the whole read; opens the file with a context manager, iterates lines, dispatches per prefix, returns (graph, nb_drones).
  • _strip_comment(line) — drops anything from # onward, trims whitespace.
  • _parse_drone_count(line) — validates and stores line 1.
  • _parse_zone_line(line, kind) — handles start_hub/end_hub/hub; extracts name, x, y, metadata; creates a Zone; enforces uniqueness and the single-start/single-end rule.
  • _parse_connection_line(line) — extracts the two zone names (split once on the last unambiguous dash), resolves them against already-known zones, checks for duplicates, creates a Connection.
  • _parse_metadata(raw) — turns [key=value ...] into a dict; applies defaults; type-checks each known key.
  • _validate_zone_type(value) — checks membership in the 4 allowed types.
  • _validate_positive_int(value, field_name) — shared validator for capacities.
  • _error(message) — raises one custom, descriptive exception carrying the line number; the only place errors are worded.
Order of operations that avoids subtle bugs
  1. Parse nb_drones first — fail fast if missing/invalid.
  2. Parse all zone lines before any connection line (connections must reference already-known zones — this ordering makes that check trivial).
  3. Only after the whole file is read: confirm exactly one start and one end hub exist.
  4. Apply "ignore max_drones on start/end" as a post-processing step on those two zones specifically, not as a general rule.

One custom exception is enough

Define a single MapParseError (subclassing Exception) carrying a message and line number. Every validation failure raises it; FlyInApp catches it once, prints a clean message, exits — satisfying "no unhandled crashes" without a maze of exception types.

PHASE 5

Graph & Domain Model

The four classes that hold the network's live state during simulation.

class Zone

  • name, x, y — identity and position.
  • zone_type — one of normal / priority / restricted / blocked.
  • color — optional, for the visualizer.
  • max_drones — capacity (unlimited sentinel for start/end).
  • occupants — a set of drone IDs currently inside.
  • entry_cost() — 1, 2, or "impossible" based on zone_type.
  • has_space(n=1) — is there room for n more drones right now?
  • add_occupant(drone_id) / remove_occupant(drone_id) — mutate occupants.
  • is_start / is_end — simple boolean properties (or a subclass, if you prefer — a flag is simpler here).

class Connection

  • zone_a, zone_b — the two Zone endpoints.
  • max_link_capacity — capacity.
  • in_transit — set of drone IDs currently traversing it.
  • other_end(zone) — given one side, return the neighbor.
  • has_space() — capacity check.
  • enter(drone_id) / leave(drone_id) — mutate in_transit.

class Drone

  • drone_id — e.g. 1 (displayed as D1).
  • current_zone — where it is right now.
  • path — the ordered list of zone names from PathFinder.
  • path_index — how far along path it is.
  • transit_state — None, or "mid-restricted-move, arriving turn N".
  • arrived — boolean.
  • next_zone() — peek at the next step in path.
  • advance() — move path_index forward, update current_zone.
  • has_arrived() — current_zone.is_end.

class Graph

  • zones — dict, name → Zone.
  • connections — list of Connection (or dict keyed by frozenset of the two names).
  • start, end — the two special Zone references.
  • add_zone(zone) / add_connection(connection) — populate the graph (called by MapParser).
  • neighbors(zone_name) — the adjacency-list lookup: which connections touch this zone.
  • get_zone(name) — safe lookup with a clear error if missing.
  • get_connection(name1, name2) — safe lookup between two known-adjacent zones.
Why an adjacency list, concretely here

Each Zone's neighbors are just "the other end of every Connection that mentions it" — you don't need a separate index structure at all if Graph.neighbors() simply filters connections by zone name (or, for speed on larger maps, precompute a dict[name, list[Connection]] once when the graph is built). Either is O(1)-ish per lookup and needs zero external dependencies.

PHASE 6

Pathfinding Strategy

One class, one job: the cheapest, priority-aware route for a single drone, ignoring other drones.

class PathFinder

  • graph — the Graph to search over.
  • find_path(start_name, end_name) — returns an ordered list of zone names, or None if unreachable (e.g. blocked-off / disconnected graph).
  • _edge_cost(destination_zone) — 1 for normal/priority, 2 for restricted, "infinite/skip" for blocked.
  • _tie_break_key(zone) — a comparison value used only when two candidate routes cost the same, favoring more priority zones.

Algorithm outline (Dijkstra, self-written, no library)

  1. Maintain a "best known cost so far" per zone, initialized to infinity except the start (0).
  2. Use a priority queue (Python's built-in heapq is allowed — it's a data structure, not a graph library) keyed by cost, with the priority-tie-break as a secondary key.
  3. Repeatedly pop the cheapest unvisited zone, skip blocked neighbors entirely, relax costs to its neighbors using _edge_cost.
  4. Stop when you pop the end zone, or the queue empties (no path exists).
  5. Reconstruct the path by walking a "came-from" map you filled in during relaxation.
Where "priority" actually gets used

Cost stays identical between normal and priority zones (both = 1). The tie-break key is what lets priority zones win when two paths reach the same zone at the same total cost — e.g. compare by (total_cost, -priority_zone_count) so cheaper wins first, and among equal-cost options the one touching more priority zones wins.

Keep it single-drone here

PathFinder should know nothing about other drones, current occupancy, or turns — that's the Simulator's job in Phase 7. Mixing the two concerns here is the most common way this project gets over-engineered; resist it.

PHASE 7

Simulation / Scheduling Engine

Where every capacity rule and the restricted-zone commitment trap actually get enforced, turn by turn.

class Simulator

  • graph, drones — the network and the fleet (each already carrying a PathFinder-computed path).
  • turn — current turn number, starts at 0.
  • reservations — dict keyed by (resource, turn) → drone id, used to lock in future slots for restricted-zone commitments.
  • log — list of turn lines, built as the simulation runs.
  • run() — loop calling step() until is_finished(); returns log.
  • step() — resolves exactly one turn: propose → resolve → apply → record.
  • _propose_moves() — for each non-arrived drone, ask "what would it like to do this turn" (advance one path step, continue a restricted transit, or wait).
  • _resolve_conflicts(proposals) — filters proposals down to the ones that are actually legal this turn, applying the departures-before-arrivals rule and the reservation table.
  • _apply_moves(approved) — mutates Zone/Connection occupancy and each Drone's state.
  • _record_turn(approved) — formats this turn's line in the required output syntax.
  • is_finished() — all drones arrived.

The turn-resolution order (this is the whole engine)

  1. Departures: every drone leaving a zone this turn frees that zone's slot immediately, in-memory, before arrivals are checked.
  2. Restricted commitments already in flight: drones due to land this turn from a 2-turn move land unconditionally (their slot was reserved when they departed) and are marked arrived-at-zone.
  3. New 1-turn moves (normal/priority): check destination zone capacity (post-departure) and, if the move uses a connection, connection capacity; approve while capacity remains, reject the rest (they wait instead).
  4. New restricted-zone departures: only allowed if the destination zone will have a free slot on arrival turn — check the reservation table, not just current occupancy; if approved, write a reservation for turn + 2 and mark the drone "in transit."
  5. Everyone else: stays in place (a valid, deliberate "wait").
Deadlock avoidance, kept simple

Because unresolved proposals simply become "wait" instead of erroring, the simulation can never crash on a conflict — worst case, drones wait extra turns. To keep the turn count competitive, the order you resolve competing proposals in matters: a simple, defendable rule is FIFO by drone ID, or "closest to the goal first." Anything more elaborate is optimization territory for Phase 10, not a mandatory requirement.

PHASE 8

Output & Visualization

Satisfy the exact log format, then add the simplest visual feedback layer on top.

Output format, non-negotiable

  • One line per turn; stationary drones omitted from that line.
  • Space-separated tokens: D<ID>-<zone> for arrivals, D<ID>-<connection> for restricted transits.
  • Printing stops the turn all drones have arrived.

Simulator._record_turn() already builds this — Visualizer just needs to print/decorate it, not recompute it.

class Visualizer

  • graph — for zone colors/positions.
  • color_map — zone name → ANSI color code, built once from each Zone.color.
  • render_turn(turn_number, line) — prints the required plain-text line, plus a colored annotation (e.g. colorize each D<ID>-<zone> token using that zone's color).
  • render_summary(total_turns, drones) — final report: total turns, optionally the secondary metrics from Phase 2.
  • render_map() (optional, simplest useful version) — a static ASCII/coordinate-based print of zones and connections before the run starts, so a viewer can orient themselves.
Simplest option that still satisfies the requirement

The subject accepts colored terminal output alone — no GUI required. ANSI escape codes (Python's built-in "\033[3xm" sequences, or the small colorama-style approach if you want an extra dependency) are enough to map each zone's declared color metadata to a visible terminal color per move. That single choice satisfies "visual representation," "documented in the README," and "colors specified in zone metadata are used" — all at once, with no graphics library.

PHASE 9

CLI, Tooling & README

Wire the classes together and satisfy every non-functional requirement.

class FlyInApp

  • args — parsed CLI arguments (map file path, optional flags like --capacity-info mentioned in the live-coding defense step).
  • run() — the only place that touches every other class: parse → build graph → pathfind per drone → simulate → visualize; wraps the whole thing in a top-level try/except around MapParseError (and any other expected failure) for a clean exit.
  • _parse_args() — thin wrapper over argparse.

main.py is then just: build a FlyInApp, call run(). That's it — the "script" is a two-line shell around the object graph.

PHASE 10

Testing, Tuning & Defense Prep

Prove correctness, sanity-check performance, and get ready to explain it live.

Build your own maps for each edge case

  • Single drone, linear path.
  • Disconnected graph (no path exists) — must fail gracefully, not crash.
  • Zero-width bottleneck (capacity 1 shared by many drones).
  • A restricted zone right next to the end hub (tests the commitment rule under time pressure).
  • Duplicate connection, invalid zone type, missing start/end — each should raise a clear MapParseError.

Sanity-check against the benchmarks

Not mandatory to hit — but any large miss is a signal your scheduler is over-waiting somewhere (usually: not preferring priority zones, or resolving conflicts in a poor order).

Defense checklist

Be ready to
  • Explain, live, why the architecture is fully OOP — point at each class's single responsibility.
  • Trace one drone's journey through Parser → Graph → PathFinder → Simulator → Visualizer out loud.
  • Explain the restricted-zone commitment rule and show where it's enforced in Simulator.
  • State your algorithm's complexity (Dijkstra: O((V+E) log V) per drone; turn resolution: O(D) per turn).
  • Perform the live-coding modification calmly: e.g. adding a --capacity-info flag — know exactly which class/method would need a one-line addition (hint: Simulator._record_turn() and FlyInApp._parse_args()).
Why is a single custom exception class enough for the whole parser?
Every parse failure needs the same two things: a human-readable message and a line number. One exception type carrying both, raised from many small validators, keeps error handling in exactly one place (the top-level catch in FlyInApp.run()) instead of scattering try/except blocks everywhere.
Why does PathFinder never look at current drone occupancy?
Because that's a scheduling concern, not a routing concern. Keeping them separate means each class stays small, testable in isolation, and easy to explain — exactly what "simplest correct solution" means in practice.

You now have the whole build order

Suggested build sequence when you actually start typing: domain.py → parser.py → a tiny manual smoke test → pathfinder.py → simulator.py → visualizer.py → main.py → Makefile/README last. Each step is independently testable before the next depends on it — that's the whole point of the split.
