STEP 00

Entry point & CLI parsing

File: src/__main__.py → calls into src/orchestrator.py

What runs first

Running python -m src maps/easy/01_linear_path.txt makes Python execute src/__main__.py, the special filename Python looks for when you run a package with -m. 

from __future__ import annotations
from orchestrator import FlyInApp


def main() -> int:
    return FlyInApp.from_argv().run()

    main()

Three things worth naming explicitly:

  • from __future__ import annotations — makes every type hint in the file (e.g. list[str], Zone | None) a plain string at runtime instead of being evaluated immediately. This is why the code can use modern syntax like str | Path even though it declares Python ≥ 3.10 support broadly — it costs nothing at import time and only matters to mypy.
  • if __name__ == '__main__': — the standard guard so that importing this module (e.g. from a test) doesn't accidentally run main().
  • main() returns an int exit code but doesn't call sys.exit() itself in this file — that plumbing is left to whatever invokes -m src at the OS level, keeping this file to 13 lines.

STEP 01

FlyInApp.run() — the whole pipeline in one function

File: src/orchestrator.py, method run()

The full method

def run(self) -> int:
    try:
        graph, nb_drones = MapParser(self.args.map).parse()
        pathfinder = PathFinder(graph)
        start = graph.start
        end = graph.end
        if start is None or end is None:
            raise MapParseError("start or end hub is missing", 0)

        paths = pathfinder.get_drones_paths(nb_drones)
        if len(paths) != nb_drones:
            print("Error: No valid paths for all drones.")
            return 1

        drones = [
            Drone(i, start, paths[i - 1])
            for i in range(1, nb_drones + 1)
        ]
        simulator = Simulator(graph, drones)
        log = simulator.run()

        for line in log:
            print(line)
        if self.args.summary:
            print(f"Total turns: {len(log)}")
        if self.args.visual:
            show_simulation(graph, log)
        return 0
    except MapParseError as e:
        print(e, file=sys.stderr)
        return 1
    except (OSError, SimulationError) as e:
        print(f"Error: {e}", file=sys.stderr)
        return 1

This one method is the pipeline diagram from the roadmap, turned into real code. Everything below in this course is one of these lines expanded to full depth, in the order they execute:

MapParser(...).parse()→ graph, nb_drones→ PathFinder(graph)→ pathfinder.get_drones_paths(n)→ paths→ Drone(...) × n→ Simulator(...).run()→ log→ print / show_simulation

The try/except wraps the entire pipeline in exactly one place — this is the "single custom exception, one top-level catch" design from Phase 4/9 of the subject brief, applied for real: MapParseError catches every malformed-map problem, SimulationError catches a runaway simulation (see Step 07), and OSError catches things like "map file doesn't exist" bubbling up from Path.open() inside the parser. Both branches print to sys.stderr (so error text doesn't pollute the drone-movement log printed to stdout) and return exit code 1.

STEP 02

MapParser(self.args.map).parse()

File: src/parser.py

MapParser.__init__ — what gets built before reading a single line

def __init__(self, filepath: str | Path) -> None:
    self.map_path = Path(filepath)
    self.graph = Graph()
    self.nb_drones = 0
    self.line_number = 0
    self.drone_count_seen = False
    self.start_seen = False
    self.end_seen = False
    self.connection_keys: set[frozenset[str]] = set()

An empty Graph() (Step 03) is created immediately — the parser's whole job is to fill it in. connection_keys is a set of frozenset objects. A frozenset({"a","b"}) equals frozenset({"b","a"}) — order doesn't matter — which is exactly how the parser later detects that connection: a-b and connection: b-a are the same duplicate connection without writing extra comparison logic.

parse() — the line-reading loop

def parse(self) -> tuple[Graph, int]:
    with self.map_path.open(encoding="utf-8") as handle:
        for self.line_number, raw_line in enumerate(handle, start=1):
            line = self.strip_comment(raw_line)
            if line:
                self.dispatch_line(line)

    if not self.drone_count_seen:
        self.error("missing required 'nb_drones:' line")
    if not self.start_seen:
        self.error("map must define exactly one start_hub")
    if not self.end_seen:
        self.error("map must define exactly one end_hub")

    return self.graph, self.nb_drones

with self.map_path.open(...) as handle: is a context manager — it guarantees the file is closed even if a MapParseError is raised halfway through, which is exactly the "context managers for files" robustness rule from the subject. Opening a file object makes it directly iterable line-by-line; wrapping it in enumerate(handle, start=1) gives you (line_number, raw_line) pairs starting at 1 instead of 0 — and because the loop variable is written straight into self.line_number, every method called afterward (all the way down into error()) automatically knows which line it's working on without needing it passed as a parameter.

For every physical line: strip_comment() runs first (see below), and if line: skips blank lines and lines that were only a comment (which strip down to an empty string). Only non-empty content reaches dispatch_line(). After the loop finishes (file fully read), three post-checks fire — these can only be checked after the whole file is seen, which is exactly the ordering rule from the roadmap ("only after the whole file is read: confirm exactly one start and one end hub exist").

→ return value

parse() returns the tuple (self.graph, self.nb_drones). Back in orchestrator.run(), this is unpacked straight into graph, nb_drones = MapParser(...).parse() — the fully-built Graph is now ready for PathFinder in Step 05.

strip_comment(line)

def strip_comment(self, line: str) -> str:
    return line.split("#", 1)[0].strip()

"...".split("#", 1) splits on the first # only (the 1 is "max splits"), so a # that could appear later in a value doesn't chop the line again. [0] takes everything before that first #, and .strip() removes leading/trailing whitespace and the trailing newline character every line from a file iterator carries.

dispatch_line(line) — routing by prefix

def dispatch_line(self, line: str) -> None:
    if line.startswith("nb_drones:"):
        self.nb_drones = self.parse_drone_count(line)
        self.drone_count_seen = True
        return

    if not self.drone_count_seen:
        self.error("the first instruction in the map must be 'nb_drones: <count>'")

    for prefix in ZONE_PREFIXES:
        if line.startswith(prefix):
            kind = prefix[:-1]
            self.parse_zone_line(line[len(prefix):], kind)
            return

    if line.startswith("connection:"):
        self.parse_connection_line(line[len("connection:"):])
        return

    self.error(f"unrecognized line type: '{line}'")

ZONE_PREFIXES = ("start_hub:", "end_hub:", "hub:") is a module-level constant. The for prefix in ZONE_PREFIXES loop tries each one in turn; on a match, prefix[:-1] strips the trailing colon to get the plain kind string ("start_hub", "end_hub", or "hub"), and line[len(prefix):] slices off the matched prefix, passing only the remainder (e.g. " start 0 0 [color=green]") onward. The early-return after every branch means at most one handler ever runs per line, and falling through all of them without an return means the line matched nothing legal — hence the final catch-all self.error(...).

This function also enforces one more ordering rule inline: if the very first non-comment/non-blank line isn't nb_drones:, drone_count_seen is still False and the very next check raises immediately — satisfying "line 1 must be nb_drones."

parse_drone_count(line)

def parse_drone_count(self, line: str) -> int:
    _, _, value = line.partition(":")
    return self.validate_positive_int(value.strip(), "nb_drones")

str.partition(":") splits into exactly 3 pieces: everything before the separator, the separator itself, and everything after — here the first two pieces are thrown away with _ (Python's conventional "I don't need this" name), keeping only value, the raw number as text. It's then handed to validate_positive_int (shared helper, described below) which does the actual int-parsing and returns a plain int. That becomes self.nb_drones back in dispatch_line.

parse_zone_line(remainder, kind) — building one Zone

def parse_zone_line(self, remainder: str, kind: str) -> None:
    head, meta_raw = self.split_metadata(remainder)
    tokens = head.split()
    if len(tokens) != 3:
        self.error("expected '<name> <x> <y>' after zone prefix")
    name, x_str, y_str = tokens

    if "-" in name:
        self.error(f"zone name '{name}' must not contain '-'")
    if name in self.graph.zones:
        self.error(f"duplicate zone name '{name}'")

    x = self.validate_integer(x_str, "x coordinate")
    y = self.validate_integer(y_str, "y coordinate")

    metadata = self.parse_metadata(meta_raw, ZONE_METADATA_KEYS)
    zone_type = metadata.get("zone", "normal")
    self.validate_zone_type(zone_type)

    max_drones_raw = metadata.get("max_drones", "1")
    max_drones: int | None = self.validate_positive_int(max_drones_raw, "max_drones")
    color = metadata.get("color")

    if kind == "start_hub":
        if self.start_seen:
            self.error("only one start_hub is allowed")
        self.start_seen = True
        max_drones = None
    elif kind == "end_hub":
        if self.end_seen:
            self.error("only one end_hub is allowed")
        self.end_seen = True
        max_drones = None

    zone = Zone(name=name, x=x, y=y, zone_type=zone_type, color=color, max_drones=max_drones)
    self.graph.add_zone(zone)
    try:
        if kind == "start_hub":
            self.graph.start = zone
        elif kind == "end_hub":
            self.graph.end = zone
    except GraphError as exc:
        self.error(str(exc))

Read top to bottom, this is doing, in order:

  1. Split off metadata via split_metadata (below), leaving head = "start 0 0" and meta_raw = "color=green".
  2. Tokenize the head with the parameterless str.split(), which splits on any run of whitespace — must yield exactly 3 tokens (name, x, y) or it's an error.
  3. Validate the name: no dash (dashes are reserved for connection syntax a-b), and not already used — name in self.graph.zones is an O(1) dict membership check since graph.zones is a dict[str, Zone] (Step 03).
  4. Parse coordinates as plain integers.
  5. Parse metadata into a small dict[str, str], then pull out zone (defaulting to "normal" via dict.get(key, default)), max_drones (defaulting to "1"), and color (defaulting to None since .get("color") has no default arg).
  6. Enforce the single-start / single-end rule and — critically — force max_drones = None on start/end hubs regardless of what the file said, which is the "ignore max_drones on start/end, as a post-processing step on those two zones specifically" rule from the roadmap. None is later read by Zone.has_space() as "unlimited."
  7. Construct the Zone object and register it with self.graph.add_zone(zone).
  8. Wire it as start/end on the graph, via property setters that can themselves raise — e.g. trying to make a blocked zone the end hub raises GraphError deep inside Graph.end's setter (Step 03); that's caught right here and re-raised as the parser's own MapParseError via self.error(str(exc)), so every failure path — whatever its origin — surfaces through the one exception type the top-level try/except in orchestrator.run() knows how to catch.

parse_connection_line(remainder) — building one Connection

def parse_connection_line(self, remainder: str) -> None:
    head, meta_raw = self.split_metadata(remainder)

    if head.count("-") != 1:
        self.error("expected 'connection: <name1>-<name2>'")
    name_a, name_b = (part.strip() for part in head.split("-", 1))

    if name_a == name_b:
        self.error(f"connection cannot link '{name_a}' to itself")
    if name_a not in self.graph.zones:
        self.error(f"connection references unknown zone '{name_a}'")
    if name_b not in self.graph.zones:
        self.error(f"connection references unknown zone '{name_b}'")

    key = frozenset({name_a, name_b})
    if key in self.connection_keys:
        self.error(f"connection '{name_a}-{name_b}' already defined")
    self.connection_keys.add(key)

    metadata = self.parse_metadata(meta_raw, CONNECTION_METADATA_KEYS)
    capacity = self.validate_positive_int(metadata.get("max_link_capacity", "1"), "max_link_capacity")

    connection = Connection(
        zone_a=self.graph.zones[name_a],
        zone_b=self.graph.zones[name_b],
        max_link_capacity=capacity,
    )
    self.graph.add_connection(connection)

head.count("-") != 1 is a strict guard: exactly one dash is allowed in the head — which is precisely why zone names may never contain a dash (enforced back in parse_zone_line): otherwise "maze-a1-maze-a2" would be ambiguous. head.split("-", 1) then confidently splits on that single dash. Both endpoint names must already exist in self.graph.zones — this is why the roadmap's ordering rule ("parse all zone lines before any connection line") matters in practice: this check would otherwise reject perfectly valid forward references. The duplicate check reuses the same frozenset trick described in __init__. Finally the real Zone objects (not just their names) are looked up from self.graph.zones and passed into Connection(...), so the Connection holds live references it can mutate later during simulation.

Two small shared helpers used above

def split_metadata(self, remainder: str) -> tuple[str, str]:
    start = remainder.find("[")
    if start == -1:
        return remainder.strip(), ""
    if not remainder.rstrip().endswith("]"):
        self.error("unterminated metadata block, missing ']'")
    end = remainder.rfind("]")
    return remainder[:start].strip(), remainder[start + 1:end].strip()

def parse_metadata(self, raw: str, allowed_keys: set[str]) -> dict[str, str]:
    metadata: dict[str, str] = {}
    if not raw:
        return metadata
    for token in raw.split():
        if token.count("=") != 1:
            self.error(f"malformed metadata token '{token}'")
        key, value = token.split("=", 1)
        if key not in allowed_keys:
            self.error(f"unknown metadata key '{key}' for this line type")
        if key in metadata:
            self.error(f"duplicate metadata key '{key}'")
        metadata[key] = value
    return metadata

split_metadata finds the first [ with str.find (returns -1 if absent — no metadata block at all is valid) and the last ] with str.rfind, so it correctly captures a metadata block even though the same character never appears twice in practice — and rejects a block that opens with [ but never closes. parse_metadata is shared by both zone and connection lines — the caller passes in which keys are legal for that line type (ZONE_METADATA_KEYS = {"zone", "color", "max_drones"} vs. CONNECTION_METADATA_KEYS = {"max_link_capacity"}), so writing max_link_capacity=2 on a hub: line is rejected as an unknown key for that context, and vice versa. 

def validate_zone_type(self, value: str) -> str: ...      # must be in ALLOWED_ZONE_TYPES
def validate_integer(self, value: str, field_name: str) -> int: ...     # int(value) or raise
def validate_positive_int(self, value: str, field_name: str) -> int: ... # validate_integer + > 0 check
def error(self, message: str) -> NoReturn:
    raise MapParseError(message, self.line_number)

validate_positive_int calls validate_integer internally — no code duplication between "must be an int" and "must be a positive int." Every single validation failure across the entire parser funnels through the one error() method, whose return type is annotated NoReturn (a typing hint telling mypy "this function never returns normally, it always raises" — useful because callers like tokens = ...; name, x_str, y_str = tokens would otherwise need a type-checker-satisfying else branch after an if error case: self.error(...)). Because self.line_number was already updated by the for loop in parse(), every MapParseError automatically carries the correct line number without threading it through every function signature.

The objects the parser is building: Zone, Connection, Graph

Files: src/domain.py (Zone, Connection), src/graph.py (Graph)

class Zone

ZONE_ENTRY_COST = {"normal": 1, "priority": 1, "restricted": 2}

class Zone:
    def __init__(self, name, x, y, zone_type="normal", color=None, max_drones=1) -> None:
        self.name, self.x, self.y = name, x, y
        self.zone_type = zone_type
        self.color = color
        self.max_drones = max_drones
        self.occupants: set[int] = set()
        self.is_start = False
        self.is_end = False

    @property
    def is_blocked(self) -> bool: return self.zone_type == "blocked"
    @property
    def is_restricted(self) -> bool: return self.zone_type == "restricted"
    @property
    def is_priority(self) -> bool: return self.zone_type == "priority"

    def entry_cost(self) -> int | None:
        if self.is_blocked: return None
        return ZONE_ENTRY_COST[self.zone_type]

    def has_space(self, n: int = 1) -> bool:
        if self.max_drones is None: return True
        return len(self.occupants) + n <= self.max_drones

    def add_occupant(self, drone_id): self.occupants.add(drone_id)
    def remove_occupant(self, drone_id): self.occupants.discard(drone_id)

occupants is a live set[int] of drone IDs — a set because membership/insert/remove are all O(1) and a drone can never occupy the same zone twice. @property turns a method into something read like an attribute (zone.is_restricted, no parentheses) while still computing it fresh from zone_type every time — no separate boolean fields to keep in sync. entry_cost() is the single source of truth for "1 turn / 2 turns / impossible" used identically by both PathFinder (Step 05, to weight edges) and Simulator (Step 08, to know if a destination is a restricted 2-turn commitment). has_space(n=1) treats max_drones is None as "unlimited" — the sentinel value the parser forces onto start/end hubs.

class Connection

class Connection:
    def __init__(self, zone_a: Zone, zone_b: Zone, max_link_capacity: int = 1) -> None:
        self.zone_a, self.zone_b = zone_a, zone_b
        self.max_link_capacity = max_link_capacity
        self.in_transit: set[int] = set()

    @property
    def name(self) -> str: return f"{self.zone_a.name}-{self.zone_b.name}"

    def other_end(self, zone: Zone) -> Zone:
        if zone is self.zone_a: return self.zone_b
        if zone is self.zone_b: return self.zone_a
        raise ValueError(...)

    def connects(self, name_a: str, name_b: str) -> bool:
        return {self.zone_a.name, self.zone_b.name} == {name_a, name_b}

    def has_space(self, n: int = 1) -> bool:
        return len(self.in_transit) + n <= self.max_link_capacity

    def enter(self, drone_id): self.in_transit.add(drone_id)
    def leave(self, drone_id): self.in_transit.discard(drone_id)

other_end(zone) uses is (object identity, not == equality) since zone_a/zone_b are the exact same Zone instances stored in Graph.zones — this is the pattern that lets Graph.neighbors() (below) turn "which connections touch this zone" into "walk to the other end" with zero extra lookups. in_transit tracks drones currently mid-corridor on a restricted 2-turn move (Step 08).

class Graph

class Graph:
    def __init__(self) -> None:
        self.zones: dict[str, Zone] = {}
        self.connections: list[Connection] = []
        self._adjacency: dict[str, list[Connection]] = {}
        self._start: Zone | None = None
        self._end: Zone | None = None

    @property
    def start(self) -> Zone | None: return self._start

    @start.setter
    def start(self, zone: Zone) -> None:
        if self._start is not None: self._start.is_start = False
        self._start = zone
        zone.is_start = True

    # .end setter is identical, plus: raises GraphError if zone.zone_type == "blocked"

    def add_zone(self, zone: Zone) -> None:
        self.zones[zone.name] = zone
        self._adjacency.setdefault(zone.name, [])

    def add_connection(self, connection: Connection) -> None:
        self.connections.append(connection)
        self._adjacency.setdefault(connection.zone_a.name, []).append(connection)
        self._adjacency.setdefault(connection.zone_b.name, []).append(connection)

    def neighbors(self, zone_name: str) -> list[Connection]:
        if zone_name not in self.zones: raise GraphError(...)
        return self._adjacency.get(zone_name, [])

_adjacency: dict[str, list[Connection]] is precisely the "precompute a dict[name, list[Connection]] once when the graph is built" optimization mentioned in the roadmap — add_zone seeds an empty list for every zone (setdefault only inserts if the key is missing, so calling it twice is safe), and add_connection appends the same Connection object onto both endpoints' lists. So neighbors("junction") is a plain O(1) dict lookup returning every Connection touching that zone — the caller then uses connection.other_end(zone) to get the actual neighboring Zone. The start/end properties use Python's setter syntax so that graph.start = zone (plain attribute-assignment syntax) secretly runs validation code and keeps Zone.is_start in sync automatically — this is why the parser (Step 02) never has to remember to set is_start itself.

reachable(start_name, end_name)

def reachable(self, start_name: str, end_name: str) -> bool:
    seen = {start_name}
    stack = [start_name]
    while stack:
        name = stack.pop()
        if name == end_name: return True
        for connection in self.neighbors(name):
            other = connection.other_end(self.zones[name])
            if other.zone_type != "blocked" and other.name not in seen:
                seen.add(other.name)
                stack.append(other.name)
    return False

This is a plain iterative DFS using a Python list as a stack (.append/.pop() from the end, both O(1)) — no recursion, so it can't hit Python's recursion limit on a large map. It completely ignores turns and capacity — it's a pure "is there any walkable route at all, skipping blocked zones" check. It's called as a cheap up-front short-circuit at the very top of PathFinder.find_path (Step 05) so that a genuinely disconnected map fails instantly instead of making the real time-aware Dijkstra search explore uselessly.

STEP 05 ★

PathFinder — reservation-aware Dijkstra, one drone at a time

File: src/pathfinder.py

Imports used in this file
  • import heapq — Python's built-in binary-heap functions (heapq.heappush, heapq.heappop). It's a plain data structure, not a graph library, which is exactly why the roadmap explicitly allows it: "Python's built-in heapq is allowed — it's a data structure, not a graph library." It operates on an ordinary Python list and keeps it in "heap order" so the smallest element is always retrievable in O(log n).
  • import math — used only for math.inf, a floating-point "infinity" sentinel for "no known cost yet."
  • from typing import Optional — Optional[list[str]] means "a list of strings, or None" (used for "no path exists").
  • State = tuple[str, int] — a type alias. Throughout this file a "state" is not just a zone name, but a (zone name, turn number) pair. This is the single most important design decision in the whole file — explained fully below.

Why the search state is (zone_name, turn), not just zone_name

A textbook Dijkstra finds the cheapest route through a static graph. But here, the graph's availability changes over time: a zone with max_drones=1 might be free at turn 3 but already reserved by an earlier drone at turn 4. So PathFinder doesn't search over "zones" — it searches over (zone, turn) pairs, called a time-expanded graph in scheduling literature. Arriving at the same zone at two different turns are two entirely different, independently-costed search nodes. This single idea is what makes later drones route around earlier drones instead of just piling into the same shortest path and fighting over capacity in the Simulator.

find_path(start_name, end_name) — the algorithm, line by line

def find_path(self, start_name: str, end_name: str) -> Optional[list[str]]:
    if not self.graph.reachable(start_name, end_name):
        self._last_schedule = []
        return None

    start_state = (start_name, 0)
    distances: dict[State, tuple[int, int]] = {start_state: (0, 0)}
    parents: dict[State, State | None] = {start_state: None}
    heap: list[tuple[int, int, int, str, int]] = [(0, 0, 0, start_name, 0)]
    visited: set[State] = set()
    counter = 0

The reachability short-circuit from Step 03 runs first. Then the search state is initialized:

  • start_state = (start_name, 0) — every drone's search begins "at the start zone, at turn 0."
  • distances maps a State to its best known (cost, -priority) pair — a 2-tuple, not just a number. Storing negative priority alongside cost means "compare cost first; on a tie, prefer whichever has more priority-zone visits" falls straight out of Python's normal tuple comparison — no custom comparator needed. This is exactly the (total_cost, -priority_zone_count) tie-break the roadmap describes.
  • parents is the classic Dijkstra "came-from" map: for every state reached, which state did we come from — used afterward to reconstruct the path by walking backwards.
  • heap is the actual priority queue passed to heapq functions. It's seeded with one 5-tuple: (cost=0, neg_priority=0, counter=0, name, turn=0).
  • counter is a strictly-increasing tie-breaker: if two heap entries ever have identical (cost, neg_priority), Python's tuple comparison would fall through to comparing the next element — which, without counter, would be the zone name str, and (with equal names too) eventually crash trying to compare incomparable types, or at best produce meaningless alphabetical tie-breaking. Putting an always-unique, monotonically increasing integer in the middle of the tuple guarantees every heap entry is fully orderable and ties break in insertion order (stable), never by comparing the tail values.

The main loop

while heap:
    cost, neg_priority, _, name, turn = heapq.heappop(heap)
    state = (name, turn)
    if state in visited:
        continue
    visited.add(state)

    if name == end_name:
        self._last_schedule = self._build_schedule(parents, state)
        return self._names(self._last_schedule)

    zone = self.graph.get_zone(name)
    priority = -neg_priority

heapq.heappop(heap) always returns the smallest tuple in the heap — since cost is first, this always pops the cheapest not-yet-finalized state, which is the whole Dijkstra guarantee: once popped, that state's cost can never improve. The if state in visited: continue guard handles "lazy deletion" — rather than removing stale heap entries when a cheaper route to the same state is found later, the code just leaves old entries in the heap and skips them here if that state was already finalized. This is a standard, simple way to use heapq (which has no efficient "decrease-key" operation) without needing a fancier heap implementation. The very first time the popped name equals end_name, the search stops — because it's the cheapest state popped so far and Dijkstra guarantees nothing cheaper remains unexplored, this is provably the optimal arrival. priority = -neg_priority converts back from the negated storage form to a normal positive count for use below.

Expanding to real neighbors (advance moves)

for connection in self.graph.neighbors(name):
    neighbor = connection.other_end(zone)
    move_cost = neighbor.entry_cost()
    if move_cost is None:
        continue                                   # blocked zone: never enterable

    arrival = turn + move_cost
    if not self._zone_available(neighbor.name, arrival):
        continue
    if not self._link_available(connection, name, neighbor.name, turn, arrival):
        continue

    next_state = (neighbor.name, arrival)
    next_priority = priority + (1 if neighbor.is_priority else 0)
    candidate = (arrival, -next_priority)
    current = distances.get(next_state, (math.inf, 0))
    if candidate >= current:
        continue

    distances[next_state] = candidate
    parents[next_state] = state
    counter += 1
    heapq.heappush(heap, (arrival, -next_priority, counter, neighbor.name, arrival))

For each connection touching the current zone:

  1. connection.other_end(zone) gets the actual neighboring Zone object (Step 03).
  2. move_cost = neighbor.entry_cost() — 1 for normal/priority, 2 for restricted, or None for blocked. A None immediately continues to the next connection — blocked zones are structurally impossible to route into, not just discouraged.
  3. arrival = turn + move_cost — the turn number the drone would land on the neighbor if it left right now.
  4. _zone_available(neighbor.name, arrival) — this is the reservation check (full mechanics below): does the destination zone still have a free slot at that specific arrival turn, given every path already reserved by earlier drones?
  5. _link_available(...) — the equivalent check for the connection's own capacity across every turn the transit would occupy it (important for the 2-turn restricted case, where the connection is "in use" for two consecutive turns, not one).
  6. If both checks pass, compute the candidate cost as (arrival, -next_priority) and compare it against the best cost known so far for that exact (neighbor, arrival) state — distances.get(next_state, (math.inf, 0)) defaults to "infinitely bad" if never seen. Relaxation only happens on strict improvement (if candidate >= current: continue skips otherwise) — standard Dijkstra relaxation, just over 2-part tuple costs instead of a single number.
  7. On improvement: record the new best cost, record the parent link for path reconstruction, and push a fresh 5-tuple onto the heap with a new unique counter value.

Waiting: the move the roadmap calls "a valid, deliberate wait"

wait_state = (name, turn + 1)
wait_key = (turn + 1, -priority)
current = distances.get(wait_state, (math.inf, 0))
if wait_key < current and turn < self._wait_limit():
    distances[wait_state] = wait_key
    parents[wait_state] = state
    counter += 1
    heapq.heappush(heap, (turn + 1, -priority, counter, name, turn + 1))

After trying every real neighbor, the loop also considers staying in the same zone for one more turn — a self-loop in the time-expanded graph from (name, turn) to (name, turn+1) at cost 1. This is what lets the algorithm express "the fastest real route is blocked by another drone's reservation right now, but will be free if I just wait one turn" — without waiting-as-a-move, a temporarily-reserved bottleneck would look like a dead end instead of a short delay. turn < self._wait_limit() caps how long the search is willing to sit still, which brings us to: 

def _wait_limit(self) -> int:
    return max(100, len(self.graph.zones) * 20)

A generous, size-scaled cap (at least 100 turns, or 20 per zone on larger maps) that exists purely to guarantee termination: without some bound, a pathologically over-reserved map could make the search explore an unbounded number of "just wait one more turn" states. It's set high enough that it never meaningfully constrains a solvable map, only guards against infinite search.

Why this is Dijkstra and not BFS

BFS finds the route with the fewest edges. Here, edges have different costs (1 for normal/priority, 2 for restricted) and the search must minimize total turns, not hop count — a 3-hop all-normal route and a 2-hop route through one restricted zone can tie or lose depending on the numbers. That's a weighted-shortest-path problem, which is what a priority queue + relaxation (Dijkstra) solves, and exactly what heapq is doing here instead of a plain FIFO queue.

The reservation system — how "multiple drones, multiple paths" actually works

def __init__(self, graph: Graph) -> None:
    self.graph = graph
    self.zone_reservations: dict[tuple[str, int], int] = {}
    self.link_reservations: dict[tuple[str, str, int], int] = {}
    self._last_schedule: list[State] = []

Two dictionaries carry state across multiple calls to find_path — this is what lets drone #2's search "see" drone #1's already-committed route:

  • zone_reservations[(zone_name, turn)] = count — how many drones are already scheduled to be occupying that zone at that exact turn.
  • link_reservations[(z1, z2, turn)] = count — how many drones are already scheduled to be transiting that connection during that turn (keys are always stored with z1, z2 = sorted((a, b)) so "a","b" and "b","a" hash to the same key — the connection is bidirectional).
def _zone_available(self, name: str, turn: int) -> bool:
    zone = self.graph.get_zone(name)
    if zone.is_end or zone.max_drones is None:
        return True
    return self.zone_reservations.get((name, turn), 0) < zone.max_drones

def _link_available(self, connection, current_name, next_name, start_turn, end_turn) -> bool:
    z1, z2 = sorted((current_name, next_name))
    capacity = connection.max_link_capacity
    for turn in range(start_turn, end_turn):
        used = self.link_reservations.get((z1, z2, turn), 0)
        if used >= capacity:
            return False
    return True

_zone_available treats the end hub (and any zone with max_drones is None, i.e. the start hub) as always available — matching the "unlimited occupancy on start/end" rule. _link_available loops over range(start_turn, end_turn) — for a normal 1-turn move that's a single turn, but for a restricted 2-turn move it checks both turns the drone would physically be mid-corridor, correctly modeling that a restricted transit occupies the connection for its whole duration, not just its arrival instant.

find_paths(nb_drones) and get_drones_paths — the loop that creates the multi-drone effect

def find_paths(self, nb_drones: int) -> list[list[str]]:
    paths: list[list[str]] = []
    if self.graph.start is None or self.graph.end is None:
        return paths
    for _ in range(nb_drones):
        path = self.find_path(self.graph.start.name, self.graph.end.name)
        if path is None:
            break
        paths.append(path)
        self._reserve_schedule(self._last_schedule)
    return paths

def get_drones_paths(self, nb_drones: int) -> list[list[str]]:
    return self.find_paths(nb_drones)

This is the actual multi-path mechanism, and it is beautifully simple: run the exact same single-drone Dijkstra, once per drone, in a plain for loop — but after each drone's path is found, immediately call self._reserve_schedule(self._last_schedule) to permanently record that route's timing into zone_reservations/ link_reservations before the next iteration's search even starts. Drone 1's search sees an empty reservation table and gets the purely-optimal route. Drone 2's search now sees drone 1's reservations as "occupied" at those exact turns via _zone_available/ _link_available, and Dijkstra naturally routes around them — either via a different physical path, or by waiting a turn, whichever is cheaper. This repeats for every drone. If at any point find_path returns None (map too constrained, or genuinely disconnected), the loop breaks early and returns however many paths it managed — which is exactly why orchestrator.run() checks if len(paths) != nb_drones: and bails out with an error message rather than silently under-provisioning drones.

Why this still allows the Simulator to do useful work

The reservations here are the pathfinder's own predicted schedule, computed by walking each path at its ideal, uncontended timing (_schedule, below). The real Simulator (Step 08) doesn't trust these turn numbers blindly — it re-resolves capacity live, turn by turn, because reality can still diverge (e.g. a drone slightly delayed by the FIFO tie-break in _resolve_moves). What the reservation table guarantees is that the routes chosen for different drones are spread out and capacity-aware from the start, so the Simulator mostly just has to execute a already-sensible plan rather than untangle everyone converging on the same single shortest path.

_reserve_schedule(schedule) — writing the reservations

def _reserve_schedule(self, schedule: list[State]) -> None:
    for index, (name, turn) in enumerate(schedule):
        zone = self.graph.get_zone(name)
        if not zone.is_start and not zone.is_end:
            key = (name, turn)
            self.zone_reservations[key] = self.zone_reservations.get(key, 0) + 1

        if index + 1 >= len(schedule):
            continue
        next_name, next_turn = schedule[index + 1]
        if name == next_name:
            continue                                       # a "wait" state — no link to reserve
        z1, z2 = sorted((name, next_name))
        for current_turn in range(turn, next_turn):
            key = (z1, z2, current_turn)
            self.link_reservations[key] = self.link_reservations.get(key, 0) + 1

schedule here is the raw list[State] — i.e. every (zone, turn) pair visited, including repeated zone names from "wait" states (unlike the deduplicated name-only path returned to the caller). Walking it with enumerate lets each step look at both "here" and "next" to know exactly which turn-slot to reserve. Start/end hubs are deliberately never reserved (if not zone.is_start and not zone.is_end) since they have unlimited capacity — reserving them would be wasted bookkeeping. When name == next_name (a wait), there's no connection to reserve, only the zone reservation already handled above. Otherwise, the connection is reserved across every turn from departure to arrival — again correctly spanning 2 turns for a restricted move.

Path reconstruction: _build_schedule and _names

def _build_schedule(self, parents, state) -> list[State]:
    schedule: list[State] = []
    current: State | None = state
    while current is not None:
        schedule.append(current)
        current = parents[current]
    schedule.reverse()
    return schedule

def _names(self, schedule: list[State]) -> list[str]:
    names: list[str] = []
    for name, _ in schedule:
        if not names or names[-1] != name:
            names.append(name)
    return names

_build_schedule walks the parents back-pointer map from the goal state all the way back to None (the start state's parent), collecting every state along the way, then .reverse()s the list in place so it reads start-to-goal. This full, turn-stamped schedule (including repeated "wait" entries) is stored on self._last_schedule so find_paths can feed it straight into _reserve_schedule without recomputing anything. _names then collapses that into the plain list[str] of distinct consecutive zone names actually returned by find_path — a zone visited across several "wait" turns in a row only appears once, since waiting doesn't change the drone's physical zone. This deduplicated list is what the Drone object (Step 06) and later the Simulator (Step 08) treat as "the path" — the Simulator re-derives its own turn-by-turn timing live rather than reusing the pathfinder's turn numbers directly.

→ return value, all the way back to orchestrator.run()

pathfinder.get_drones_paths(nb_drones) ultimately returns paths: list[list[str]] — one deduplicated zone-name list per drone, in drone order. Back in run(), this becomes paths[i - 1] handed to each new Drone in Step 06.

One more small method: reserve(path)

def reserve(self, path: list[str]) -> None:
    schedule = self._schedule(path)
    self._reserve_schedule(schedule)

def _schedule(self, path: list[str]) -> list[State]:
    schedule: list[State] = [(path[0], 0)]
    turn = 0
    for name in path[1:]:
        cost = self.graph.get_zone(name).entry_cost() or 1
        turn += cost
        schedule.append((name, turn))
    return schedule

This is a public convenience method not called anywhere in the current pipeline (it isn't invoked from orchestrator.run()) — it exists so a caller (e.g. a test, or a future feature) can reserve an already-known path without having gone through find_path first. _schedule rebuilds a plausible turn-by-turn State list for an arbitrary path by simply walking it and adding each zone's entry_cost() (defaulting to 1 via or 1 if somehow None) — assuming no waiting was needed, i.e. the "ideal" timing.

class Drone

class Drone:
    def __init__(self, drone_id: int, start_zone: Zone, path: list[str]) -> None:
        self.drone_id = drone_id
        self.current_zone = start_zone
        self.path = path
        self.path_index = 0
        self.transit_state: TransitState | None = None
        self.arrived = False

    @property
    def label(self) -> str: return f"D{self.drone_id}"

    def next_zone_name(self) -> str | None:
        next_index = self.path_index + 1
        if next_index >= len(self.path):
            return None
        return self.path[next_index]

    def advance(self, zone: Zone) -> None:
        self.path_index += 1
        self.current_zone = zone
        self.transit_state = None
        if zone.is_end:
            self.arrived = True

    def begin_transit(self, state: TransitState) -> None:
        self.transit_state = state

    def has_arrived(self) -> bool:
        return self.arrived

path_index always points at the drone's current position within its own path list; next_zone_name() just peeks one ahead without mutating anything, returning None once there's nothing left (drone is already on its last path entry, the end hub). advance(zone) is the only method that actually moves the drone forward: bump the index, update current_zone, clear any leftover transit_state, and flip arrived = True the moment the new zone is the end hub (zone.is_end, set by the Graph.end property in Step 03). All of this is called exclusively from the Simulator (Step 08) — the Drone class itself never decides when or whether to move.

Simulator(graph, drones).run() — the outer loop

class SimulationError(Exception): ...

class Simulator:
    def __init__(self, graph: Graph, drones: list[Drone], max_turns: int = DEFAULT_MAX_TURNS) -> None:
        self.graph = graph
        self.drones = drones
        self.max_turns = max_turns
        self.turn = 0
        self.reservations: dict[tuple[str, int], set[int]] = {}
        self.log: list[str] = []
        for drone in drones:
            drone.current_zone.add_occupant(drone.drone_id)

    def run(self) -> list[str]:
        while not self.is_finished():
            if self.turn >= self.max_turns:
                raise SimulationError(f"simulation did not finish within {self.max_turns} turns")
            self.step()
        return self.log

    def is_finished(self) -> bool:
        return all(drone.has_arrived() for drone in self.drones)

The constructor loop for drone in drones: drone.current_zone.add_occupant(drone.drone_id) physically places every drone into the start hub's occupants set before turn 1 even begins — matching the mental model "all drones start in one start_hub." self.reservations is a separate reservation table from PathFinder's — this one belongs to the live turn-by-turn engine and only ever holds next-turn restricted-zone arrival slots (Step 08). is_finished() uses the builtin all(...) over a generator expression — short-circuits as soon as any drone reports has_arrived() == False, so it doesn't need to check every drone once one blocker is found. run() is a plain while loop calling step() repeatedly, guarded by max_turns=10_000 so a genuinely un-completable schedule (which shouldn't happen given a reachable map, but could in principle from a bug or a pathological map) raises SimulationError instead of hanging forever — this is the error caught back in orchestrator.run()'s except (OSError, SimulationError) branch.

STEP 08

step() — resolving exactly one turn

File: src/simulator.py

def step(self) -> None:
    self.turn += 1
    landed = self._process_arrivals()
    landed_ids = {drone.drone_id for drone, _ in landed}
    proposals = self._propose_moves(landed_ids)
    approved = self._resolve_moves(proposals)
    self.log.append(self._record_turn(landed, approved))

Five sub-steps, executed in this exact order every turn — and the order is the whole scheduling policy, matching the roadmap's "process all departures first, then check capacity for arrivals" and "restricted commitments already in flight land unconditionally" rules.

8a. _process_arrivals() — land anyone due this turn

def _process_arrivals(self) -> list[tuple[Drone, str]]:
    landed: list[tuple[Drone, str]] = []
    for drone in self.drones:
        state = drone.transit_state
        if state is None or state.arrival_turn != self.turn:
            continue
        state.connection.leave(drone.drone_id)
        self._release(state.destination.name, self.turn, drone.drone_id)
        state.destination.add_occupant(drone.drone_id)
        drone.advance(state.destination)
        landed.append((drone, state.destination.name))
    return landed

Loops over every drone; skips any drone that isn't mid-transit, or whose reservation was for a different turn. For every drone landing exactly this turn: free its connection slot (connection.leave), release the reservation table entry that was holding its destination seat (_release, below), physically add it as an occupant of the destination zone, and call drone.advance(destination) (Step 06) which updates its position/path index and — if the destination is the end hub — marks it arrived. This lands unconditionally: because the slot was already reserved two turns ago when the drone departed (8c below), there's no capacity check to redo here, matching "restricted commitments already in flight land unconditionally (their slot was reserved when they departed)."

8b. _propose_moves(landed_ids) — what would each drone like to do?

def _propose_moves(self, landed_ids: set[int]) -> list[Proposal]:
    proposals: list[Proposal] = []
    for drone in self.drones:
        if drone.has_arrived() or drone.transit_state is not None or drone.drone_id in landed_ids:
            continue
        next_name = drone.next_zone_name()
        if next_name is None:
            continue
        destination = self.graph.get_zone(next_name)
        connection = self.graph.get_connection(drone.current_zone.name, next_name)
        proposals.append(Proposal(drone, connection, destination))
    return proposals

Three drone states are explicitly excluded from proposing a new move this turn: already arrived, still mid-transit on an earlier restricted move, or a drone that just landed this very turn (its drone_id is in the landed_ids set built in step()) — a freshly-landed drone waits until next turn before proposing its next hop, which is a natural consequence of processing one action per drone per turn. Proposal (a small @dataclass like TransitState) simply bundles the drone with its desired destination zone and the connection it would travel on — no decision-making happens here yet, only intent-gathering.

8c. _resolve_moves(proposals) — the actual scheduler

def _resolve_moves(self, proposals: list[Proposal]) -> list[ApprovedMove]:
    for proposal in proposals:
        proposal.drone.current_zone.remove_occupant(proposal.drone.drone_id)

    approved: list[ApprovedMove] = []
    ordered = sorted(proposals, key=lambda item: item.drone.drone_id)
    for proposal in ordered:
        drone, destination, connection = proposal.drone, proposal.destination, proposal.connection
        restricted = destination.is_restricted

        space = self._future_space(destination) if restricted else destination.has_space()

        if not (space and connection.has_space()):
            drone.current_zone.add_occupant(drone.drone_id)
            continue

        connection.enter(drone.drone_id)
        if restricted:
            arrival_turn = self.turn + 1
            self._reserve(destination.name, arrival_turn, drone.drone_id)
            drone.begin_transit(TransitState(connection, destination, arrival_turn))
        else:
            destination.add_occupant(drone.drone_id)
            drone.advance(destination)
            connection.leave(drone.drone_id)

        approved.append(ApprovedMove(drone, connection, destination, restricted))
    return approved

This is the heart of the whole simulation, so unpacking it fully:

  1. Departures first. The very first thing that happens — before any capacity check — is every proposing drone is removed from its current zone's occupants. This is the literal implementation of "departures free up space within the same turn" and "process all departures first, then check capacity for arrivals." A zone with max_drones=1 holding one drone that wants to leave now genuinely has a free slot for a different incoming drone in this same turn.
  2. Deterministic ordering. sorted(proposals, key=lambda item: item.drone.drone_id) processes proposals in ascending drone-ID order — this is the "FIFO by drone ID" tie-break rule the roadmap flags as "simple, defendable." When two drones compete for the same last free slot, the lower-numbered drone always wins.
  3. Capacity check, branching on zone type. For a restricted destination, capacity is checked via _future_space (below) instead of the zone's plain has_space(), because a restricted move doesn't land this turn — it must reserve a slot for next turn, accounting for anyone else already promised that same slot. For any other zone type, the ordinary destination.has_space() (Step 03) is enough since the move completes immediately. Either way, the connection itself is also checked with connection.has_space() — both conditions must hold (if not (space and connection.has_space())).
  4. Rejection = wait, not error. If either check fails, the drone is simply put back into its current zone's occupants (drone.current_zone.add_occupant(...), undoing step 1 for this drone only) and the loop continues to the next proposal — no exception, no special "waiting" state object is even created; a drone that isn't in approved this turn implicitly stayed put, which is exactly how _record_turn (8d) ends up correctly omitting it from the output line. This is the "unresolved proposals simply become wait instead of erroring" deadlock-avoidance design from the roadmap.
  5. Approval, branching again on zone type. If approved: connection.enter(...) marks it in transit either way. For a restricted move: compute arrival_turn = self.turn + 1 (always exactly one turn away — the drone departs now, arrives next turn, since restricted costs 2 turns total: this departure turn plus the arrival turn handled by _process_arrivals next cycle), call self._reserve(...) to lock that future slot, and call drone.begin_transit(...) (Step 06) to record the commitment — note the drone is not added to the destination's occupants yet; it's genuinely mid-corridor, not physically in either zone, matching "no mid-corridor waiting, no cancelling." For a normal/priority move: it completes immediately in this same turn — destination.add_occupant(...), drone.advance(...), and the connection is freed again right away with connection.leave(...) since a 1-turn hop never actually needs to "hold" the link across a turn boundary.
  6. Either way, an ApprovedMove record is appended, carrying whether it was restricted — used purely for output formatting next.

_future_space(zone) — the restricted-zone reservation check

def _future_space(self, zone: Zone) -> bool:
    if zone.max_drones is None:
        return True
    reserved = len(self.reservations.get((zone.name, self.turn + 1), set()))
    return len(zone.occupants) + reserved + 1 <= zone.max_drones

This answers "if I additionally commit one more drone to arrive here next turn, will it still fit?" — it adds together currently physically present occupants, already-promised future arrivals (reserved, from self.reservations), and the + 1 for the drone being considered right now, and compares the sum against max_drones. This is exactly the "reserve before you commit... confirm the destination slot will be free on arrival turn" rule — checked against the reservation table, not just current occupancy, so two drones can't both depart toward the same single restricted-zone slot in the same turn. 

def _reserve(self, zone_name: str, turn: int, drone_id: int) -> None:
    key = (zone_name, turn)
    self.reservations.setdefault(key, set()).add(drone_id)

def _release(self, zone_name: str, turn: int, drone_id: int) -> None:
    key = (zone_name, turn)
    slots = self.reservations.get(key)
    if slots is None: return
    slots.discard(drone_id)
    if not slots:
        del self.reservations[key]

A reservation is a set[int] of drone IDs keyed by (zone, turn) — setdefault lazily creates the set on first use. _release (called back in 8a once the drone actually lands) removes it from that set and tidies up the dict entry entirely once empty, so self.reservations never accumulates stale keys for turns that have already passed.

8d. _record_turn(landed, approved) — building the output line

def _record_turn(self, landed, approved) -> str:
    tokens: list[tuple[int, str]] = []
    for drone, zone_name in landed:
        tokens.append((drone.drone_id, f"{drone.label}-{zone_name}"))
    for move in approved:
        target = move.connection.name if move.restricted else move.destination.name
        tokens.append((move.drone.drone_id, f"{move.drone.label}-{target}"))
    tokens.sort(key=lambda item: item[0])
    return " ".join(token for _, token in tokens)

Every drone that either finished landing this turn (from 8a) or had a move approved this turn (from 8c) contributes exactly one token, paired with its drone_id purely so the final tokens.sort(...) can order the line by drone number regardless of the order drones happened to be processed in. The token format branches on whether the approved move was restricted: a normal arrival token is D<id>-<zone_name> (using move.destination.name), while a restricted departure token uses move.connection.name (the "a-b" string from Connection.name, Step 03) since the drone hasn't arrived anywhere yet — it's announcing which corridor it just entered. This exactly matches the required output syntax: D<ID>-<zone> for arrivals, D<ID>-<connection> for in-flight restricted moves. Drones that neither landed nor got an approved move (i.e. they waited, rejected in 8c, or had nothing left to propose) simply never appear in tokens — "stationary drones omitted from that turn's line," satisfied for free by only ever adding tokens for actual events.

→ return value

The joined string (one line, or an empty string if literally nothing moved that turn — which can happen if every drone is waiting) is appended to self.log. Once is_finished() finally becomes true, run() returns the complete log: list[str] back to orchestrator.run().

Coordinate pipeline: _fit(), _layout(), _place(), _screen_pos()

def _fit(self) -> tuple[tuple[float, float], tuple[float, float]]:
    zones = list(self.graph.zones.values())
    xs = [z.x for z in zones] or [0]
    ys = [z.y for z in zones] or [0]
    span_x = max(max(xs) - min(xs), 1)
    span_y = max(max(ys) - min(ys), 1)
    sx = (self.width - 2 * MARGIN) / span_x
    sy = (self.height - 2 * MARGIN) / span_y
    offset = (MARGIN - min(xs) * sx, MARGIN - min(ys) * sy)
    return (sx, sy), offset

def _layout(self, zone_name: str) -> tuple[float, float]:
    zone = self.graph.zones[zone_name]
    sx, sy = self.zoom
    ox, oy = self.origin
    return zone.x * sx + ox, zone.y * sy + oy

def _place(self, x: float, y: float) -> tuple[float, float]:
    return x + self.cam[0], y + self.cam[1]

def _screen_pos(self, zone_name: str) -> tuple[float, float]:
    return self._place(*self._layout(zone_name))

Four small functions, each adding exactly one transformation, composed together:

  1. _fit() looks at every zone's raw map x/y (the coordinates straight from the map file, Step 02), finds the bounding box (span_x, span_y, each floored at 1 to avoid division by zero on a degenerate single-column/row map), and computes an independent horizontal scale sx and vertical scale sy so the whole map's bounding box exactly fills the window minus a MARGIN of 120 pixels on every side. The offset then shifts everything so the map's minimum x/y lands exactly at the margin, not at the literal screen origin. This runs once at startup and again on every window resize.
  2. _layout(zone_name) applies that scale+offset to one zone's raw coordinates — this is the zone's position in "world space," ignoring any camera pan.
  3. _place(x, y) adds the current self.cam pan offset — turning world space into actual screen space.
  4. _screen_pos(zone_name) is just the composition of the two: raw map coordinate → world layout → panned screen position. This is the function almost everything in on_draw actually calls.
Why split into 4 functions instead of 1

Panning (via arrow keys) changes every frame, but the zoom/fit only changes on resize. Separating "world layout" (stable) from "camera placement" (volatile) means _layout()'s result for a zone can be reused (e.g. cached in self.pos for drones sitting still) without recomputing the scale math, while panning only ever adds two numbers in _place().

_start_positions() — where every drone begins the replay

def _start_positions(self) -> dict[int, str]:

        return {}
    highest = 0
    for line in self.log:
        for token in line.split():
            highest = max(highest, int(token[1:].split("-", 1)[0]))
    return {d: self.graph.start.name for d in range(1, highest + 1)}

Notice the visualizer is never told nb_drones directly — it only receives graph and the plain text log. So it re-derives the drone count by scanning every token of every log line: a token looks like "D3-junction"; token[1:] strips the leading "D", .split("-", 1)[0] takes everything before the first dash (the numeric ID — this correctly stops before a connection name like "3-junction-goal" would ever be ambiguous, since IDs never contain a dash), and int(...) converts it. Tracking the running max across the whole log gives the highest drone ID ever mentioned, which (since drone IDs are always 1..nb_drones) is exactly nb_drones. Every drone then starts the replay "parked" at the start hub's name.

The animation state machine: on_update(dt)

MOVE_TIME = 0.6
HOLD_TIME = 0.9

def on_update(self, dt: float) -> None:
    for key in self.keys_held:
        dx, dy = ARROWS[key]
        self.cam[0] += dx * PAN_SPEED * dt
        self.cam[1] += dy * PAN_SPEED * dt

    if self.paused or self.turn >= len(self.log):
        return

    if not self.moves and not self.holding:
        self._start_turn()
    self.timer += dt
    if not self.holding and self.timer >= MOVE_TIME:
        self.timer, self.holding = 0.0, True
    elif self.holding and self.timer >= HOLD_TIME:
        self._finish_turn()

Called every frame with dt = real elapsed seconds (typically ~1/60s). First, camera panning is completely independent of playback — it applies even while paused: for every key currently held down (tracked in self.keys_held, populated by on_key_press/on_key_release below), ARROWS[key] looks up a unit direction (dx, dy) and moves the camera at a constant PAN_SPEED pixels/second, scaled by dt so panning speed is frame-rate independent.

Then, if paused or the replay has consumed every log line, nothing else happens this frame. Otherwise this is a small two-phase state machine per turn:

  1. Idle → Moving: if there's no in-progress interpolation (self.moves is empty) and we're not in the post-move hold, call _start_turn() to compute this turn's start/end positions for every drone that moves (below).
  2. Moving: accumulate self.timer every frame; once it reaches MOVE_TIME (0.6 seconds), snap to the "holding" phase and reset the timer — drones have now visually finished sliding to their destination.
  3. Holding: once the (separately timed) hold reaches HOLD_TIME (0.9 seconds — a pause so the eye can register the arrival before the next turn starts sliding), call _finish_turn() to commit positions and advance to the next log line.

So the perceived rhythm per turn is: 0.6s of sliding animation, then 0.9s of static hold, then the next turn's slide begins — entirely independent of how much real simulated time (in "turns") that log line represents.

_start_turn() — turning one log line into interpolation targets

def _start_turn(self) -> None:
    self.moves.clear()
    for token in self.log[self.turn].split():
        drone_id = int(token[1:].split("-", 1)[0])
        target = token.split("-", 1)[1]
        start = self.pos[drone_id]
        if target in self.graph.zones:
            self.moves[drone_id] = (start, self._layout(target), target)
            self.midway.discard(drone_id)
        else:
            a, b = target.split("-", 1)
            pa, pb = self._layout(a), self._layout(b)
            mid = ((pa[0] + pb[0]) / 2, (pa[1] + pb[1]) / 2)
            self.moves[drone_id] = (start, mid, None)
            self.midway.add(drone_id)
            self.edge_of[drone_id] = (a, b)

self.log[self.turn] is the raw text line for the current turn, e.g. "D1-roof2 D2-tunnelB"; .split() breaks it into individual space-separated tokens. For each token, the drone ID is extracted the same way as in _start_positions, and target is everything after the first dash — which could be either a plain zone name (a normal arrival) or a "a-b" connection name (a restricted departure). The code distinguishes the two cases with one clean check: if target in self.graph.zones — zone names never collide with connection names because connection names always contain a dash and zone names are never allowed to (enforced back in the parser's "-" in name check, Step 02).

  • Arrival case: self.moves[drone_id] = (start, self._layout(target), target) — animate a straight line from the drone's last known screen position to the target zone's world position, and remember the target name (used by _finish_turn to update zone_of). self.midway.discard(drone_id) ensures a drone that was mid-flight last turn is no longer flagged as such.
  • Restricted-departure case: the token has no matching zone, so it's split on the dash into its two endpoint zone names a, b, both endpoints are laid out in world space, and the animation target becomes the literal midpoint between them — visually, the drone slides halfway down the corridor and pauses there, rather than jumping straight to a zone it hasn't reached yet. The stored tuple's third element is None (not a real zone), which is exactly the signal _finish_turn uses to know "don't update this drone's logical zone, it's still traveling." The drone is added to self.midway and its edge recorded in self.edge_of so _draw_connections can highlight that specific line segment.

_finish_turn() and _arrived()

def _finish_turn(self) -> None:
    for drone_id, (_, end, target) in self.moves.items():
        self.pos[drone_id] = end
        if target is not None:
            self.zone_of[drone_id] = target
    self.moves.clear()
    self.turn += 1
    self.timer = 0.0
    self.holding = False

def _arrived(self) -> dict[int, str]:
    if not self.holding:
        return {}
    return {d: t for d, (_, _, t) in self.moves.items() if t is not None}

_finish_turn commits every animated drone's final screen position into self.pos, and — only for drones that actually reached a real zone ( target is not None) — updates their logical zone_of entry too (a mid-flight drone keeps its old zone_of value, since it hasn't logically arrived anywhere new yet). Then it clears self.moves, advances the replay cursor self.turn += 1, and resets the timer/hold flag ready for on_update to call _start_turn() again next frame. _arrived() is a small query used only during the drawing pass (below): while holding (the pause after sliding finishes), which drones just landed in a real zone this turn — used so those drones are drawn merged into the zone's occupant wedge rather than as a separate floating dot on top of it.

Pass 1 — _draw_connections()

def _draw_connections(self) -> None:

Pass 2 — _draw_zones() and the n-gon geometry helpers

def _ngon_point(cx, cy, radius, angle, sides, rotation=ROTATION) -> tuple[float, float]:
    seg = 2 * math.pi / sides
    local = ((angle - rotation + seg / 2) % seg) - seg / 2
    r = radius * math.cos(seg / 2) / math.cos(local)
    return cx + r * math.cos(angle), cy + r * math.sin(angle)

def _ngon_vertices(cx, cy, radius, sides, rotation=ROTATION) -> list[tuple[float, float]]:
    step = 2 * math.pi / sides
    return [_ngon_point(cx, cy, radius, rotation + i * step, sides, rotation) for i in range(sides)]

This is genuinely the most mathematically dense part of the file, so it's worth walking through slowly. A regular polygon with sides sides and "radius" radius (distance from center to each corner) has corners spaced every 2π / sides radians apart. _ngon_vertices is the simple case: it just calls _ngon_point at each of those exact corner angles (rotation + i * step) to get the hexagon/pentagon's actual corner coordinates — this is what's fed to arcade.draw_polygon_outline/draw_polygon_filled.

_ngon_point is more general: it computes a point on the polygon's boundary at an arbitrary angle, not just at a corner — used later by _draw_occupants to slice a hexagon into uneven pie-wedges at angles that don't line up with its corners. The math: for a regular polygon, the distance from the center to the boundary varies between the "radius" (at a corner) and a slightly smaller value (at the midpoint of an edge) — the classic formula for that distance at angle offset local from the nearest edge's center is radius * cos(seg/2) / cos(local), where seg is the angular width of one edge. local = ((angle - rotation + seg/2) % seg) - seg/2 folds the requested angle into the range [-seg/2, seg/2] relative to its nearest edge's center, using Python's modulo operator % (which always returns a non-negative result for a positive divisor) — this is what makes the formula work identically no matter which of the polygon's edges the angle actually falls on. Once r (the boundary distance at that exact angle) is known, standard polar-to-Cartesian conversion (cx + r*cos(angle), cy + r*sin(angle)) gives the final point. 

def _draw_zones(self) -> None:
    moving = set(self.moves)
    arrived = self._arrived()
    for name, idx in self._zone_number.items():
        zone = self.graph.zones[name]
        x, y = self._screen_pos(name)
        ring = self._zone_color(zone)
        sides = 5 if (zone.is_start or zone.is_end) else 6
        arcade.draw_polygon_outline(_ngon_vertices(x, y, self.zone_r + 2, sides), ring, 2)

        occupants = sorted(
            [d for d, z in self.zone_of.items() if z == name and d not in moving]
            + [d for d, z in arrived.items() if z == name]
        )
        if occupants:
            self._draw_occupants(x, y, sides, occupants)
        else:
            fill = tuple(max(c // 5, 20) for c in ring)
            arcade.draw_polygon_filled(_ngon_vertices(x, y, self.zone_r, sides), fill)
            letter = ("S" if zone.is_start else "E" if zone.is_end else zone.zone_type[0].upper())
            self.labels.draw(f"letter-{name}", letter, x, y - 8, ring, 16, anchor_x="center", bold=True)

        self.labels.draw(f"name-{name}", name, x, self._name_label_y(y, idx), TEXT, 9, anchor_x="center")

For every zone: pick its ring color via _zone_color (below), pick 5 sides for start/end hubs and 6 for everything else (visually distinguishing the two special hubs at a glance), and draw the outline slightly larger (self.zone_r + 2) than the fill so the ring reads as a border. Then it builds the list of drone IDs currently "in" this zone — combining drones logically parked there (self.zone_of) that aren't currently mid-slide (d not in moving, where moving = set(self.moves)) with drones that just froze there this frame during the hold phase (arrived, from _arrived()) — sorted(...) on the combined list both deduplicates concerns about ordering and gives a stable, predictable wedge order. If the zone has any occupants, delegate to _draw_occupants (below) instead of a plain fill. Otherwise draw a plain dim fill (fill = tuple(max(c // 5, 20) for c in ring) — each RGB channel of the ring color divided by 5, floored at 20, i.e. a darker tint of the same hue) and a single centered letter identifying the zone: "S"/"E" for start/end, or the first letter of its zone_type (upper-cased) otherwise — "N"/"P"/"R"/"B". Finally the zone's plain text name is drawn near it, offset above or below via _name_label_y (alternating by idx % 2, purely to reduce label collisions between adjacent zones).

_draw_occupants — pie-slicing a zone by drone count

def _draw_occupants(self, x, y, sides, drones: list[int]) -> None:
    n = len(drones)
    step = 2 * math.pi / n
    for i in range(n):
        a0, a1 = i * step, (i + 1) * step
        samples = max(2, int(math.degrees(step) / 10))
        arc = [_ngon_point(x, y, self.zone_r, a0 + (a1 - a0) * k / samples, sides) for k in range(samples + 1)]
        arcade.draw_polygon_filled([(x, y), *arc], WHITE)
    for i in range(n if n > 1 else 0):
        ax, ay = _ngon_point(x, y, self.zone_r, i * step, sides)
        arcade.draw_line(x, y, ax, ay, BG, 2)
    if n <= 6:
        r = self.zone_r * 0.55 if n > 1 else 0
        for i, drone_id in enumerate(drones):
            mid = (i + 0.5) * step
            self.labels.draw(f"d{drone_id}", f"D{drone_id}", x + r * math.cos(mid), y + r * math.sin(mid) - 6, BG, 10, anchor_x="center", bold=True)

This divides the zone's polygon into n equal angular wedges, one per occupying drone. step = 2π / n is each wedge's angular width. For each wedge i: rather than approximating the polygon's curved-looking boundary segment with a single straight line (which would look faceted for a hexagon sliced into, say, 5 wedges at odd angles), the code samples several points along the polygon's actual boundary between the wedge's start and end angles using _ngon_point — samples is chosen adaptively as roughly one sample per 10 degrees of arc (max(2, ...) guarantees at least a triangle even for a huge wedge), then arcade.draw_polygon_filled([(x, y), *arc], WHITE) draws a filled fan from the center point through all those boundary samples — a "pie slice" that hugs the hexagon's actual edges rather than cutting a straight chord across them. A second loop draws thin background-colored dividing lines from the center out to each wedge boundary corner, visually separating adjacent wedges. Finally, if there are 6 or fewer occupants (beyond that, individual labels would be illegibly cramped), each wedge gets a centered "D<id>" label positioned at the wedge's angular midpoint, pulled slightly toward the center (r = zone_r * 0.55) so it sits inside its own slice rather than at the outer edge.

Pass 3 — _draw_moving_drones()

def _draw_moving_drones(self) -> None:
    arrived = self._arrived()

        if drone_id in arrived:

        arcade.draw_circle_filled(x, y, MOVE_R, WHITE)
        arcade.draw_circle_outline(x, y, MOVE_R + 1, BG, 2)
        self.labels.draw(f"d{drone_id}", f"D{drone_id}", x, y - 5, BG, 9, anchor_x="center", bold=True)

Any drone that's currently animating (in self.moves) but hasn't yet merged into a zone's wedge (not in arrived — i.e. it's either still sliding, or it's paused at a corridor midpoint) is drawn as a plain floating white circle with its label, using _drone_screen_pos: 

def _drone_screen_pos(self, drone_id: int) -> tuple[float, float]:
    start, end, _ = self.moves[drone_id]
    t = 1.0 if self.holding else min(self.timer / MOVE_TIME, 1.0)
    return self._place(start[0] + (end[0]-start[0]) * t, start[1] + (end[1]-start[1]) * t)

Classic linear interpolation ("lerp"): t is the fraction of the move completed, clamped to [0, 1] via min(self.timer / MOVE_TIME, 1.0) while actively sliding, or forced to exactly 1.0 during the hold phase (fully arrived at its interpolation target — which, remember, might just be a corridor midpoint for a restricted move). start + (end - start) * t is the standard lerp formula applied separately to x and y, and the result is passed through _place one more time so the drone also respects the current camera pan.

Pass 4 — _draw_hud() and the _TextPool trick

class _TextPool:
    def __init__(self) -> None:
        self._items: dict[str, arcade.Text] = {}

    def draw(self, key, text, x, y, color, size, anchor_x="left", bold=False) -> None:
        item = self._items.get(key)
        if item is None:
            item = arcade.Text(text, x, y, color, size, anchor_x=anchor_x, bold=bold)
            self._items[key] = item
        else:
            item.text, item.x, item.y, item.color = text, x, y, color
        item.draw()

Arcade's own documentation warns that calling the convenience function arcade.draw_text() every frame is slow, because it silently creates a brand-new arcade.Text object (with its own internal font-rendering setup) every single call — at 60 frames per second with a dozen text labels, that's hundreds of throwaway objects per second. _TextPool fixes this with a simple object pool keyed by a caller-chosen string key (e.g. f"d{drone_id}", f"name-{name}"): the first time a given key is drawn, a real arcade.Text object is created and cached in self._items; every subsequent call with that same key just mutates the existing object's .text/.x/.y/.color fields in place and re-.draw()s it — no new allocation. This is why every drawing call in this file goes through self.labels.draw(...) instead of calling Arcade's text function directly. 

def _draw_hud(self) -> None:
    self.labels.draw("title", "FLY-IN", 30, self.height - 40, TEXT, 20, bold=True)
    status = "paused" if self.paused else "running"
    self.labels.draw("status", f"turn {min(self.turn+1, len(self.log))}/{len(self.log)}  {status}", self.width-260, self.height-38, TEXT, 13)
    self.labels.draw("controls", "arrows: pan camera   space: pause   r: replay", 30, 28, TEXT, 12)

A fixed title, a live "turn X/Y running/paused" counter (min(self.turn+1, len(self.log)) keeps the displayed turn number from ever showing one past the last real turn once the replay is finished), and a static one-line reminder of the keyboard controls.

Color resolution: _zone_color(zone)

TYPE_COLOR = {"normal": (120,126,138), "priority": (52,211,153), "restricted": (167,139,250), "blocked": (60,64,74)}

@staticmethod
def _zone_color(zone) -> tuple[int, int, int]:
    if zone.is_start: return START_COLOR
    if zone.is_end: return END_COLOR
    if zone.color: return NAMED_COLOR.get(zone.color.lower(), TYPE_COLOR["normal"])
    return TYPE_COLOR[zone.zone_type]

A clear priority order, checked top to bottom: the start hub is always cyan, the end hub is always yellow — regardless of anything the map file said — because being the unique start/end is more visually important than any custom color. Otherwise, if the map file supplied a color= metadata value (Step 02's Zone.color field), look it up in the small NAMED_COLOR table (case-insensitive via .lower()), falling back to the generic "normal" gray if the named color isn't recognized rather than crashing. Failing that, fall back to a color purely driven by the zone's type — every restricted zone is violet, every priority zone is green, etc., which is a genuinely useful visual even on maps that never set an explicit color= at all.

Kicking it off: show_simulation(graph, log)

def show_simulation(graph: Graph, log: list[str]) -> None:
    Visualizer(graph, log)
    arcade.run()

Constructing a Visualizer runs its __init__ (which, via super().__init__, registers the new window with Arcade's internal window manager — this is why the object doesn't need to be assigned to a variable; Arcade keeps track of it globally once created). arcade.run() is a blocking call: it starts Arcade's main event loop, which repeatedly calls on_update then on_draw on every open window, dispatches keyboard/mouse events to on_key_press/etc., and only returns once every Arcade window has been closed by the user. This is why show_simulation is the very last thing orchestrator.run() calls before its own return 0 — nothing after it executes until the visualization window is closed.

Why does PathFinder run once per drone in a simple loop, instead of a single multi-agent search?
Because true optimal multi-agent pathfinding (solving for all drones jointly) is NP-hard, as the roadmap notes. Running independent single-agent Dijkstra searches, but making each one aware of every previous drone's reserved (zone, turn) and (link, turn) slots, gets almost all of the benefit — later drones naturally avoid earlier drones' routes or wait for them — at a tiny fraction of the implementation and runtime cost.
Why does the Simulator not simply trust the turn numbers PathFinder computed?
PathFinder's reservations are an idealized prediction made while looking only at earlier drones' plans. The real Simulator resolves capacity live and breaks ties by drone ID (Step 8c) — a drone can end up delayed by exactly this tie-breaking in a way the pathfinder's static reservation table didn't predict. So the Simulator re-derives arrivals turn by turn from the deduplicated zone-name path, rather than replaying PathFinder's exact schedule.
Where would you add a --capacity-info flag, concretely?
Add it in FlyInApp._parse_args as another store_true argument, then in Simulator._record_turn (Step 8d) append extra per-token detail (e.g. current/max occupancy of the destination zone) when a flag is threaded through — the cleanest path is passing the flag into Simulator.__init__ so _record_turn can read it directly without new parameters on every call.

One-paragraph mental model to keep

MapParser turns text into live objects. PathFinder runs the same time-aware Dijkstra once per drone, remembering every previous drone's reservations so later drones route around earlier ones. Simulator then re-executes those plans turn by turn, the only place capacity is actually enforced live, always freeing departures before checking arrivals and breaking ties by drone ID. Visualizer is a pure playback layer on top of the finished text log — it never touches simulation logic, it only interpolates positions between the zones the log already names.
