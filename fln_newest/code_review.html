Invocation & command-line parsing main.py

When the grader runs python3 main.py maps/easy/01_linear_path.txt, Python executes main.py top to bottom. The last two lines are the classic guard: 

if __name__ == "__main__":
    main()

__name__ is a variable Python sets automatically. When the file is run directly it equals the string "__main__"; when it is imported by another module it equals "main". This guard means "only start the program if this file was launched directly", which lets other files (like your tests, if you add them) import from main.py without accidentally re-running the CLI.

Pipeline.from_argv — building the parser

class Pipeline:
    def __init__(self, args: argparse.Namespace) -> None:
        self.args = args

    @classmethod
    def from_argv(cls, argv: Sequence[str] | None = None) -> "Pipeline":
        parser = argparse.ArgumentParser(
            description="Route a fleet of drones through a Fly-In map."
        )
        parser.add_argument("map", type=Path, help="path to the map file")
        parser.add_argument("--no-color", action="store_true", ...)
        parser.add_argument("--map-info", action="store_true", ...)
        parser.add_argument("--summary", action="store_true", ...)
        parser.add_argument("--visual", action="store_true", ...)
        return cls(parser.parse_args(argv))

Pipeline is a tiny wrapper class: its only field is self.args, the argparse.Namespace object that holds every flag's value (args.map, args.summary, args.visual, …). @classmethod plus the cls(...) call at the end is the standard "alternate constructor" pattern — it lets you build a Pipeline straight from raw argv without a caller ever touching argparse directly. Four store_true flags default to False and flip to True the moment they appear on the command line — that's argparse's shorthand for a boolean switch with no value attached.

    try:

        drones = [                                                   # → §5
            Drone(i, graph.start, paths[i - 1])
            for i in range(1, nb_drones + 1)

        log = Simulator(graph, drones).run()                         # → §6

        if self.args.visual:

Two exception types are caught by name (MapParseError) or by tuple ((OSError, SimulationError)), each mapped to exit code 1. Every other exception (a real bug) is left to propagate and crash with a full traceback — deliberately, so a genuine programming error is never silently swallowed. The function's own return value (0 or 1) becomes the process's exit code via main():

parse() — the driving loop

def parse(self) -> tuple[Graph, int]:
    with self.map_path.open(encoding="utf-8") as handle:
        for self.line_number, raw_line in enumerate(handle, start=1):
            line = raw_line.split("#", 1)[0].strip()
            if line:
                self.dispatch_line(line)

    if not self.drone_count_seen:
        self.error("missing required 'nb_drones:' line")
    if not self.start_seen:
        self.error("map must define exactly one start_hub")
    if not self.end_seen:
        self.error("map must define exactly one end_hub")

    for name, zone in self.graph.zones.items():
        if not zone.is_start and not zone.is_end and len(
                self.graph.neighbors(name)) < 2:
            self.error(f"zone '{name}' must connect to at least two other zones")
    if not self.graph.connected():
        self.error("map graph is disconnected: some zones are unreachable")

    return self.graph, self.nb_drones
  • with ... open(...) as handle — a context manager: the file is guaranteed to be closed even if parsing raises partway through.
  • enumerate(handle, start=1) — iterating a file object yields one line at a time (a memory-cheap, streaming read); start=1 makes line numbers match what a human sees in a text editor, which is exactly what ends up in every MapParseError.
  • raw_line.split("#", 1)[0].strip() — splits on the first # only (maxsplit=1), keeps the part before it, and strips whitespace. This is how comments are stripped and how a comment appearing after real content on the same line (hub: a 1 1 # note) is handled — it is not a separate comment-detection branch, it is baked into every line's very first transformation.
  • The final two checks run only after every line has been read, because they are whole-graph properties: does every non-hub zone have at least two neighbors, and is the whole map one connected component (via Graph.connected(), a plain iterative DFS using a Python list as a stack — explained in §3).

dispatch_line — routing one line to the right handler

def dispatch_line(self, line: str) -> None:
    key, _, remainder = line.partition(":")
    key = key.strip()

    if key == "nb_drones":
        self.nb_drones = self.validate_positive_int(remainder.strip(), "nb_drones")
        self.drone_count_seen = True
        return

str.partition(":") splits into exactly three parts — (before, ":", after) — even if ":" never appears (then before is the whole string and the other two are empty). The very first check enforces that nb_drones: must be the first real line in the file — every other keyword is rejected until it has been seen.

split_metadata & parse_metadata — the [key=value ...] block

def split_metadata(self, remainder: str) -> tuple[str, str]:
    start = remainder.find("[")
    if start == -1:
        return remainder.strip(), ""
    if not remainder.rstrip().endswith("]"):
        self.error("unterminated metadata block, missing ']'")
    end = remainder.rfind("]")
    return remainder[:start].strip(), remainder[start + 1:end].strip()

str.find locates the first [ (or returns -1 if there is none, meaning "no metadata at all"); str.rfind locates the last ], so everything strictly between the outermost brackets is treated as one metadata blob, even if it contains stray characters. parse_metadata then tokenizes that blob on whitespace and, per token, requires exactly one = (token.count("=") != 1 rejects both zone with no = and a=b=c with two), checks the key is one of the allowed keys for that line type, and rejects duplicate keys within the same block.

Graph — owns everything, answers adjacency queries

class Graph:
    def __init__(self) -> None:
        self.zones: dict[str, Zone] = {}
        self.connections: list[Connection] = []
        self.adjacency: dict[str, list[Connection]] = {}
        self.start: Optional[Zone] = None
        self.end: Optional[Zone] = None

    def add_zone(self, zone: Zone) -> None:
        self.zones[zone.name] = zone
        self.adjacency.setdefault(zone.name, [])

    def add_connection(self, connection: Connection) -> None:
        self.connections.append(connection)
        self.adjacency[connection.zone_a.name].append(connection)
        self.adjacency[connection.zone_b.name].append(connection)

adjacency is the actual adjacency list: a dict mapping every zone name to the list of Connection objects touching it. Registering a connection appends it under both of its endpoints — since every connection is bidirectional, this one list serves traffic in either direction, and it's exactly what neighbors() hands back: 

def neighbors(self, zone_name: str) -> list[Connection]:
    if zone_name not in self.zones:
        raise GraphError(f"unknown zone '{zone_name}'")
    return self.adjacency[zone_name]

This is the single function every graph-walking algorithm in the project calls to "look around" from a zone — the parser's connectivity checks, reachable(), connected(), and (most importantly) every expansion step of Dijkstra in PathFinder.

reachable() and connected() — the two DFS utilities

def reachable(self, start_name: str, end_name: str) -> bool:
    seen = {start_name}
    stack = [start_name]
    while stack:
        name = stack.pop()
        if name == end_name:
            return True
        for connection in self.neighbors(name):
            other = connection.other_end(self.zones[name])
            if other.zone_type != "blocked" and other.name not in seen:
                seen.add(other.name)
                stack.append(other.name)
    return False

This is an iterative depth-first search using a plain Python list as a stack (.pop() without an index removes from the end — O(1), and that's what makes this a stack rather than a queue). It walks only through non-blocked zones, so it answers "ignoring permanently-closed zones, can a drone in principle ever reach the goal from here?" — used as a cheap early-exit before running the much more expensive time-aware Dijkstra in §4. connected() is the same DFS shape but starting from an arbitrary zone and checking that every zone in the map gets visited — that's the "is the whole graph one connected component" check called at the very end of MapParser.parse().

  • heapq — the standard-library binary min-heap. It only ever operates on plain Python lists via free functions (heapq.heappush, heapq.heappop); it compares whatever tuples you push using ordinary tuple comparison (element by element, left to right), which is the entire reason every item pushed here is a carefully-ordered tuple — the ordering of the tuple is the priority policy.

The core idea: search over (zone, turn), not just zone

A textbook Dijkstra finds the cheapest route through a graph of places. This one searches a graph of (place, time) pairs: 

State = tuple[str, int]   # (zone_name, turn)

Every node the search visits is "which zone, at which turn". This single design decision is what makes the whole file a genuine multi-drone scheduler and not just a shortest-path routine — it lets later drones' searches see and avoid the exact turns earlier drones will occupy a zone or a link, not merely which zones exist.

zone_available / link_available — reading the reservation tables

def zone_available(self, name: str, turn: int) -> bool:
    zone = self.graph.get_zone(name)
    if zone.is_end or zone.max_drones is None:
        return True
    return self.zone_reservations.get((name, turn), 0) < zone.max_drones

def link_available(self, name_a, name_b, capacity, start_turn, end_turn) -> bool:
    z1, z2 = sorted((name_a, name_b))
    for turn in range(start_turn, end_turn):
        if self.link_reservations.get((z1, z2, turn), 0) >= capacity:
            return False
    return True

self.zone_reservations is a dict[(zone_name, turn) -> count] and self.link_reservations is a dict[(zone_a, zone_b, turn) -> count], both built fresh on PathFinder.__init__ and grown by every drone routed so far — this is the whole "reservation table" the class name promises. Note sorted((name_a, name_b)): since a connection has no inherent direction, the two zone names are always sorted alphabetically before being used as a key, so travelling A→B and B→A hit the exact same reservation slot. Also note the special case: the end hub is always available (zone.is_end) and any zone with max_drones is None (start/end) is always available — matching the parser's decision to give start/end unlimited capacity.

find_path — the search loop, line by line

def find_path(self, start_name: str, end_name: str) -> Optional[list[str]]:
    if not self.graph.reachable(start_name, end_name):
        return None

    start_state = (start_name, 0)
    distances: dict[State, tuple[int, int]] = {start_state: (0, 0)}
    parents: dict[State, Optional[State]] = {start_state: None}
    heap: list[tuple[int, int, int, str, int]] = [(0, 0, 0, start_name, 0)]
    visited: set[State] = set()
    wait_limit = max(100, len(self.graph.zones) * 20)
    counter = 0

The graph-reachability check (§3) is a cheap early exit before the more expensive time-aware search runs at all. distances maps every visited (zone, turn) state to the best (cost, -priority) found so far for it (cost = the turn itself, since every step spends exactly its entry cost in turns; -priority is explained below). parents is the "came-from" map used to rebuild the winning path once the search finishes. counter is a strictly-increasing tiebreaker: because heap entries are 5-tuples and Python compares tuples element by element, once two entries have identical (cost, -priority), the comparison falls through to counter — this exists purely so that heapq never has to compare the fourth element (a plain string, comparable but semantically meaningless here) and, more importantly, so ties are always broken by insertion order. That single design choice is the real explanation for the backtracking behaviour — see the callout after the main loop. 

    while heap:

Classic Dijkstra shape: pop the cheapest unvisited state, skip it if it was already finalized through a cheaper route (the visited check — this is what makes a lazily-deleted heap correct even though stale duplicate entries are never explicitly removed from it). The moment the popped state's zone name is the goal, the search stops immediately — because it's a min-heap, the very first time the goal is popped it is guaranteed to be via the cheapest possible route, so there is no need to keep searching. 

        zone = self.graph.get_zone(name)
        priority = -neg_priority

        for connection in self.graph.neighbors(name):
            neighbor = connection.other_end(zone)
            move_cost = neighbor.entry_cost()
            if move_cost is None:
                continue                                    # blocked zone: no edge at all

            arrival = turn + move_cost
            if not self.zone_available(neighbor.name, arrival):
                continue                                    # zone full at that turn
            if not self.link_available(name, neighbor.name,
                                        connection.max_link_capacity, turn, arrival):
                continue                                    # link full for that whole span

            next_state = (neighbor.name, arrival)
            next_priority = priority + (1 if neighbor.is_priority else 0)
            candidate = (arrival, -next_priority)
            if candidate >= distances.get(next_state, (math.inf, 0)):
                continue                                    # not an improvement

            distances[next_state] = candidate
            parents[next_state] = state
            counter += 1
            heapq.heappush(heap, (arrival, -next_priority, counter, neighbor.name, arrival))

For every connection touching the current zone: entry_cost() being None means the neighbor is blocked — the loop continues, so blocked zones are structurally unreachable, not merely "expensive". arrival = turn + move_cost is where the restricted zone's 2-turn cost actually enters the search: stepping into a restricted zone jumps the schedule two turns into the future in a single hop, exactly like a normal zone jumping one turn. Both capacity checks (zone_available, link_available) must pass or the edge is skipped for this specific turn — it may well become legal one turn later, which is exactly why the search explores many turns, not just many zones. next_priority only increases when the neighbor is a priority zone: this is the tie-break the subject asks for ("preferred in pathfinding") — encoded as a second heap key (-next_priority) rather than a cost reduction, so priority zones never make a route arrive earlier, only make an equal-cost route win over another equal-cost route with fewer priority zones. The comparison candidate >= distances.get(...) is strict Dijkstra relaxation: a state is only re-expanded if the new route genuinely beats the best one recorded for it so far (lower turn, or equal turn with more priority zones). 

        wait_state = (name, turn + 1)
        wait_key = (turn + 1, -priority)
        if turn < wait_limit and wait_key < distances.get(wait_state, (math.inf, 0)):
            distances[wait_state] = wait_key
            parents[wait_state] = state
            counter += 1
            heapq.heappush(heap, (turn + 1, -priority, counter, name, turn + 1))

This is the "stay in place for one more turn" edge — a self-loop in the time-expanded graph, costing exactly one turn, same as any normal move. It is pushed after every neighbor edge in the same iteration of the outer loop, so it always receives a strictly larger counter than any neighbor move discovered in that same step. If the whole heap empties without ever popping end_name, no route exists at all (can happen if reservations from earlier drones have sealed off every surviving route within wait_limit turns) and the function returns None.

Deep-dive nuance worth knowing (not a defense-blocking bug) The wait branch never calls zone_available. Only moving into a new zone is checked against the live reservation count before being added to the search frontier — "staying" is not. In practice this rarely bites, because reserve_schedule() (below) still records a reservation for every turn a drone's final schedule spends in a zone, including waits, so later drones' moves into that zone are still correctly blocked. And even if two plans ever disagreed, the Simulator (§6) is the real-time authority: it independently re-checks live capacity before approving any move, so a plan can never actually overfill a zone at runtime — only the offline schedule bookkeeping is slightly permissive. This is a legitimate, defensible design nuance to name proactively if asked "is waiting ever really capacity-checked?".

Why drones retreat to start or shuffle instead of waiting

This is the part of your defense worth rehearsing word for word, because it is provably true of your own code and your own maps — not a hypothetical. Running maps/hard/02_capacity_hell.txt (12 drones, three single-capacity gates) and printing every drone's planned path gives real evidence:

D5 (len=9): start -> gate2 -> waiting_area2 -> priority_bypass2 -> waiting_area2 -> priority_bypass2 -> convergence -> final_bottleneck -> goal D10 (len=12): start -> gate1 -> start -> gate1 -> waiting_area1 -> priority_bypass1 -> waiting_area1 -> priority_bypass1 -> priority_bypass2 -> convergence -> final_bottleneck -> goal

D5 genuinely oscillates between two different zones (waiting_area2 ↔ priority_bypass2) instead of parking in one place. D10 does something even more visible: it leaves gate1, flies all the way back to start, then re-enters gate1 two turns later. Both patterns come directly out of PathFinder.find_path, and here is exactly why:

  1. Waiting and moving cost the same. Every normal-zone move costs exactly 1 turn, and the self-wait edge also costs exactly 1 turn. There is nothing in the cost model that makes "stand still" cheaper than "hop to a neighbor and hop back" — both spend two turns to end up in the same place.
  2. Neighbor moves are always pushed onto the heap before the wait edge, in the same expansion. Look again at the loop: the for connection in self.graph.neighbors(name): block runs to completion, and only after it finishes does the wait block get evaluated. Both increment the same counter, so any neighbor-move discovered in this step receives a strictly smaller counter than the wait discovered in the same step.
  3. heapq breaks ties by whichever tuple is smaller, and counter is the tiebreaker once cost and priority tie. So whenever a same-turn, same-priority neighbor move exists, it is preferred over waiting purely by insertion order — the search doesn't "choose" to move for any strategic reason, it simply records that state first, and once a state is in distances/parents the (strictly-worse-or-equal) wait alternative is never able to overwrite it.
  4. The forced move only matters when the direct forward move is temporarily blocked. Drones 1–9 were planned first and have already locked in specific (zone, turn) reservation slots via reserve_schedule(). When D10's search reaches gate1, its one useful neighbor (waiting_area1) is not free at the very next turn — some earlier drone already reserved that exact slot. D10's only same-cost neighbor still open at that turn is start (unlimited capacity, always available). By point 3, that move wins the tie over simply waiting at gate1. One turn later, from start, the same logic runs again — and by then the earlier reservation at gate1 has expired, so re-entering it is now the cheapest move available. Two turns, net zero displacement, functionally identical to "waiting two turns" — just implemented as two real hops because a real hop was, at every single step, at least as cheap as standing still and was discovered first.
How to defend this choice in the review Frame it explicitly as prioritized (sequential) cooperative pathfinding over a time-expanded graph — a standard, published technique for multi-agent routing (closely related to what the literature calls "Cooperative A*"): each drone is routed in turn against a shared reservation table built by every drone routed before it, so the search space is not "zones" but "zones × time". In that space, waiting is not a special primitive with its own priority — it is just one more edge with the same cost as any other, so the search legitimately treats "stand still" and "step away and step back" as interchangeable whenever both are available, and picks whichever is discovered first by the heap. The behaviour is a direct, provable consequence of a uniform per-turn cost model combined with FIFO tie-breaking, not an accident or a hidden bug — and it is exactly what lets a later-planned drone dodge a bottleneck a fixed number of turns without ever needing to re-plan an earlier drone's already-committed route (which would be far more expensive and would risk deadlock). You can also point out you verified it is bounded and safe: the wait_limit guard (max(100, zones * 20)) stops the search from waiting forever, and the Simulator independently re-validates every move in real time, so even a suboptimal plan can never violate a live capacity constraint.

build_schedule, names, reserve_schedule — turning the search result into a path

def build_schedule(self, parents, state) -> list[State]:
    schedule: list[State] = []
    current: Optional[State] = state
    while current is not None:
        schedule.append(current)
        current = parents[current]
    schedule.reverse()
    return schedule

def names(self, schedule: list[State]) -> list[str]:
    names: list[str] = []
    for name, _ in schedule:
        if not names or names[-1] != name:
            names.append(name)
    return names

build_schedule walks the parents map backward from the goal to the start (each state points to the state it came from) and then reverses the list — the standard way to reconstruct a path from a Dijkstra "came-from" map. names() then collapses consecutive duplicate zone names — this is the mechanism that would hide a genuine "wait in the exact same zone" from the final path (since (name, t) and (name, t+1) both collapse to one name entry), which is precisely why real waits are invisible in Drone.path, while a bounce through a different zone (like start) survives the collapse and shows up as a real, visible hop — the asymmetry that makes the backtracking pattern visible in your simulation log while genuine standing-still never is. 

def reserve_schedule(self, schedule: list[State]) -> None:
    for index, (name, turn) in enumerate(schedule):
        zone = self.graph.get_zone(name)
        if not zone.is_start and not zone.is_end:
            key = (name, turn)
            self.zone_reservations[key] = self.zone_reservations.get(key, 0) + 1

        if index + 1 >= len(schedule):
            continue
        next_name, next_turn = schedule[index + 1]
        if name == next_name:
            continue                          # a wait step reserves no link
        z1, z2 = sorted((name, next_name))
        for current_turn in range(turn, next_turn):
            link_key = (z1, z2, current_turn)
            self.link_reservations[link_key] = self.link_reservations.get(link_key, 0) + 1

This walks the un-collapsed, turn-stamped schedule (not the collapsed names list) and permanently commits every (zone, turn) and every (zone_a, zone_b, turn) the winning route actually used, incrementing a running count rather than setting a flag — this is what lets a zone be legitimately shared by several drones up to its max_drones, and what the next drone's zone_available/link_available checks read back. Once committed, a reservation is never released or renegotiated — this is a strictly first-come-first-served planner: drone 1 gets the unconstrained optimum, drone 2 plans around drone 1's reservations, and so on, which is also why later-indexed drones in a congested map are the ones you'll see doing the retreating.

def get_drones_paths(self, nb_drones: int) -> list[list[str]]:

        return paths

run() / is_finished() / step() — the outer loop

def run(self) -> list[str]:
    while not self.is_finished():
        if self.turn >= self.max_turns:
            raise SimulationError(...)
        self.step()
    return self.log

def is_finished(self) -> bool:
    return all(drone.has_arrived() for drone in self.drones)

def step(self) -> None:
    self.turn += 1
    landed = self.process_arrivals()
    landed_ids = {drone.drone_id for drone, _ in landed}
    proposals = self.propose_moves(landed_ids)
    approved = self.resolve_moves(proposals)
    self.log.append(self.record_turn(landed, approved))

all(... for ...) is a generator expression fed to the built-in all() — short-circuits the moment any drone hasn't arrived, and is True vacuously once every drone has. Each call to step() runs a strict four-phase turn, always in this order: finish anything that was already in flight, ask every remaining drone what it wants to do next, referee those requests, then write down what actually happened. This ordering matters: arrivals are resolved before new proposals are collected, so a zone a drone just vacated this instant is visible as free to this same turn's proposals.

process_arrivals — completing restricted (2-turn) moves

def process_arrivals(self) -> list[tuple[Drone, str]]:
    landed: list[tuple[Drone, str]] = []
    for drone in self.drones:
        state = drone.transit_state
        if state is None or state.arrival_turn != self.turn:
            continue

        state.connection.leave(drone.drone_id)
        slots = self.reservations.get((state.destination.name, self.turn))
        if slots is not None:
            slots.discard(drone.drone_id)
            if not slots:
                del self.reservations[(state.destination.name, self.turn)]

        state.destination.add_occupant(drone.drone_id)
        drone.advance(state.destination)
        landed.append((drone, state.destination.name))
    return landed

Every drone carries at most one TransitState (§3) while mid-flight through a restricted zone's 2-turn move. This method checks every drone for "is your committed arrival turn exactly right now" — if so, it frees the connection (connection.leave), releases the destination reservation it made when the move started, physically places the drone into the destination zone (add_occupant), and calls drone.advance(destination) — which (§3) bumps path_index, updates current_zone, clears transit_state, and flags arrived if this was the end hub. The returned landed list (drone, zone name) feeds directly into this turn's output line.

propose_moves — what does every active drone want to do?

def propose_moves(self, landed_ids: set[int]) -> list[Proposal]:
    proposals: list[Proposal] = []
    for drone in self.drones:
        if (drone.has_arrived() or drone.transit_state is not None
                or drone.drone_id in landed_ids):
            continue
        next_name = drone.next_zone_name()
        if next_name is None:
            continue
        destination = self.graph.get_zone(next_name)
        connection = self.graph.get_connection(drone.current_zone.name, next_name)
        proposals.append(Proposal(drone, connection, destination))
    return proposals

Three reasons a drone is skipped this turn: it already arrived, it's still mid-flight on a restricted move (its next real decision only happens on arrival), or it just landed this very turn (it doesn't get to also move again in the same turn it arrived — landed_ids enforces exactly one action per drone per turn). Otherwise it peeks its next required zone (next_zone_name(), §3) and looks up the live Zone and Connection objects for it — this is a genuinely fresh, real-time lookup, completely independent of whatever PathFinder assumed the state of the world would be at this turn.

resolve_moves — the referee, and where real "waiting" actually happens

def resolve_moves(self, proposals: list[Proposal]) -> list[ApprovedMove]:
    for proposal in proposals:
        proposal.drone.current_zone.remove_occupant(proposal.drone.drone_id)

    approved: list[ApprovedMove] = []
    for proposal in sorted(proposals, key=lambda item: item.drone.drone_id):
        drone = proposal.drone
        destination = proposal.destination
        connection = proposal.connection
        restricted = destination.is_restricted

        if restricted:
            reserved = len(self.reservations.get((destination.name, self.turn + 1), set()))
            space = destination.max_drones is None or (
                len(destination.occupants) + reserved + 1 <= destination.max_drones)
        else:
            space = destination.has_space()

        if not (space and connection.has_space()):
            drone.current_zone.add_occupant(drone.drone_id)
            continue                                    # rejected: physically stays put

        connection.enter(drone.drone_id)
        if restricted:
            arrival_turn = self.turn + 1
            self.reservations.setdefault((destination.name, arrival_turn), set()).add(drone.drone_id)
            drone.begin_transit(TransitState(connection, destination, arrival_turn))
        else:
            destination.add_occupant(drone.drone_id)
            drone.advance(destination)
            connection.leave(drone.drone_id)

        approved.append(ApprovedMove(drone, connection, destination, restricted))
    return approved

First, every proposing drone is provisionally removed from its current zone's occupant set — this frees its own slot so that, if two drones on the same map are trying to swap zones this exact turn, neither blocks the other purely by "still standing in the way". Proposals are then resolved in strict sorted(... key=drone_id) order — a simple, deterministic, reproducible tie-break: lower drone IDs always get first claim on a contested slot. For a restricted-zone destination, space is computed against occupants plus already-reserved future arrivals plus this candidate (+ 1) — this is what stops more drones from committing to a restricted zone than it can hold once they all land one turn later, even though none of them are physically there yet. For a normal destination, it's the simple Zone.has_space() check (§3). If either the destination or the connection lacks space, the move is rejected: the drone is put back into its current zone's occupants (add_occupant) and the loop continues — this is the actual, physical, runtime "wait". Nothing about the drone's plan changes; next turn propose_moves will offer the exact same destination again, and it keeps retrying every turn until it is approved. A normal-zone move that is approved advances the drone immediately in the same call (drone.advance(destination)); a restricted-zone move that is approved does not advance the drone yet — it only commits the connection and reserves the destination, and the actual arrival (and advance() call) happens one turn later, back in process_arrivals.

Two different notions of "wait", side by side Planning-time wait (§4): a self-loop edge in Dijkstra's time-expanded search, tied in cost with any same-turn move and usually losing that tie — this is why a drone's plan almost never literally contains "stand still", and instead sometimes contains a visible bounce.

Runtime wait (here): a proposal genuinely rejected by resolve_moves because live occupancy or link capacity is full right now — the drone stays exactly where it is and is simply omitted from this turn's output line (see record_turn next). This can happen even to a drone whose plan never anticipated it, because the plan was computed against a reservation table, not against what other drones' proposals actually do turn by turn — the Simulator is the ultimate, unavoidable source of truth.

record_turn — producing the exact required output format

def record_turn(self, landed, approved) -> str:
    tokens: list[tuple[int, str]] = []
    for drone, zone_name in landed:
        tokens.append((drone.drone_id, f"{drone.label}-{zone_name}"))
    for move in approved:
        target = move.connection.name if move.restricted else move.destination.name
        tokens.append((move.drone.drone_id, f"{move.drone.label}-{target}"))
    tokens.sort(key=lambda item: item[0])
    return " ".join(token for _, token in tokens)

ngon_point / ngon_vertices — the only real math in the file

def ngon_point(cx, cy, radius, angle, sides, rotation=ROTATION) -> tuple[float, float]:
    seg = 2 * math.pi / sides
    local = ((angle - rotation + seg / 2) % seg) - seg / 2
    r = radius * math.cos(seg / 2) / math.cos(local)
    return cx + r * math.cos(angle), cy + r * math.sin(angle)

This answers a genuinely non-trivial question: "given a regular polygon of sides sides centered at (cx, cy) with circumradius radius, where is the point on its boundary at an arbitrary angle — not necessarily a vertex?" A regular polygon's edge is closer to the center than its circumradius except exactly at the vertices, so you can't just use (cx + radius·cos θ, cy + radius·sin θ) (that traces a circle, not the polygon). The trick: seg is the angular width of one polygon side; local folds the input angle into [-seg/2, seg/2] — its offset from the nearest edge's midpoint — using Python's modulo operator % (which, on floats, still returns a value with the same sign as the divisor, keeping this wrap-around correct). r = radius · cos(seg/2) / cos(local) is the standard formula for the distance from a regular polygon's center to its edge at a given angular offset from that edge's midpoint (the edge's perpendicular distance from center is radius·cos(seg/2) — the apothem — and dividing by cos(local) projects that back out to the actual point on the edge at this specific angle). This single helper is what lets draw_occupants (below) slice a hexagon into exact pie-wedges that still hug the hexagon's straight edges instead of drawing a circle. 

def ngon_vertices(cx, cy, radius, sides, rotation=ROTATION) -> list[tuple[float, float]]:
    step = 2 * math.pi / sides
    return [ngon_point(cx, cy, radius, rotation + i * step, sides, rotation) for i in range(sides)]

Calling ngon_point exactly at each vertex angle (i * step) collapses the formula above back to the simple circumradius case — this is just a convenience wrapper used whenever the code wants the polygon's actual corner points (for outlines and fills), while ngon_point alone is used when an arbitrary boundary point is needed (wedge dividers).

TextPool — why arcade.Text objects are reused, not recreated

class TextPool:
    def __init__(self) -> None:
        self.items: dict[str, arcade.Text] = {}

    def draw(self, key, text, x, y, color, size, anchor_x="left", bold=False) -> None:
        item = self.items.get(key)
        if item is None:
            item = arcade.Text(text, x, y, color, size, anchor_x=anchor_x, bold=bold)
            self.items[key] = item
        else:
            item.text, item.x, item.y, item.color = text, x, y, color
        item.draw()

arcade.Text objects are relatively expensive to construct (they prepare a GPU-backed text batch). At 60 frames a second, constructing a brand-new arcade.Text every frame for every zone label and every drone label would be wasteful. TextPool is a tiny cache keyed by a caller-chosen string (e.g. f"letter-{name}", f"d{drone_id}"): the first time a given key is drawn, a real arcade.Text is built and stored; every later call for the same key just mutates its existing .text/.x/.y/.color fields in place and re-draws it — the object is created once per unique label for the whole run.

fit / layout / place / screen_pos — the coordinate pipeline

def fit(self) -> tuple[tuple[float,float], tuple[float,float]]:
    zones = list(self.graph.zones.values())
    xs = [z.x for z in zones] or [0]
    ys = [z.y for z in zones] or [0]
    span_x = max(max(xs) - min(xs), 1)
    span_y = max(max(ys) - min(ys), 1)
    sx = (self.width - 2 * MARGIN) / span_x
    sy = (self.height - 2 * MARGIN) / span_y
    return (sx, sy), (MARGIN - min(xs) * sx, MARGIN - min(ys) * sy)

Map coordinates in the input file are small hand-picked integers (0 0, 3 4, …) with no relationship to pixels. fit() computes one scale factor per axis independently (sx for x, sy for y — this is the "independent per-axis scaling" mentioned in your project notes) so that the map's bounding box exactly fills the window minus a MARGIN border on every side, regardless of whether the map is wide, tall, or square. max(..., 1) guards against a division by zero if every zone shares the same x or y. The returned origin offset is exactly the translation that puts the map's minimum x/y at the left/bottom margin. 

def layout(self, zone_name: str) -> tuple[float, float]:
    zone = self.graph.zones[zone_name]
    sx, sy = self.zoom
    ox, oy = self.origin
    return zone.x * sx + ox, zone.y * sy + oy

def place(self, x: float, y: float) -> tuple[float, float]:
    return x + self.cam[0], y + self.cam[1]

def screen_pos(self, zone_name: str) -> tuple[float, float]:
    return self.place(*self.layout(zone_name))

Three clean layers, each doing exactly one job: layout() is the fixed world position of a zone (map coordinates through the fit() transform); place() applies only the live camera pan (self.cam, changed by arrow keys — see on_update below); screen_pos() composes both, and is the one function everything else in the class actually calls when it needs "where do I draw this zone right now". Splitting these means panning the camera never has to touch or recompute the underlying layout — it's a pure additive offset applied at draw time.

start_turn / finish_turn / arrived — the per-turn animation state machine

def start_turn(self) -> None:
    self.moves.clear()
    for token in self.log[self.turn].split():
        drone_id = int(token[1:].split("-", 1)[0])
        target = token.split("-", 1)[1]
        start = self.pos[drone_id]
        if target in self.graph.zones:
            self.moves[drone_id] = (start, self.layout(target), target)
            self.midway.discard(drone_id)
        else:
            a, b = target.split("-", 1)
            pa, pb = self.layout(a), self.layout(b)
            mid = ((pa[0]+pb[0])/2, (pa[1]+pb[1])/2)
            self.moves[drone_id] = (start, mid, None)
            self.midway.add(drone_id)
            self.edge_of[drone_id] = (a, b)

This is where the raw text log actually gets interpreted. Each token's target is checked against self.graph.zones — if it names a real zone, the token means "arrived at (or moving directly into) that zone", so the animation target is that zone's layout() position and the third tuple element (the eventual resting zone) is set. If the target is not a zone name, it must be a connection token like "a-b" (a restricted move in progress): the code splits it back into its two endpoints, computes the geometric midpoint between them, and animates the drone only halfway there, with the third tuple element set to None — meaning "don't merge into any zone's wedge yet, you're still in transit". This is exactly how the log's textual distinction between D<id>-<zone> and D<id>-<connection> becomes two different animations. 

def finish_turn(self) -> None:
    for drone_id, (_, end, target) in self.moves.items():
        self.pos[drone_id] = end
        if target is not None:
            self.zone_of[drone_id] = target
    self.moves.clear()
    self.turn += 1
    self.timer = 0.0
    self.holding = False

Called once a held/finished animation is over: every drone's resting pos snaps to the animation's end point, and if it reached a real zone (target is not None) its logical zone_of is updated too (a mid-connection drone keeps its old zone_of until it truly lands). Then the turn counter advances and the per-turn timer resets, ready for start_turn() to run again next frame. 

def arrived(self) -> dict[int, str]:
    if not self.holding:
        return {}
    return {drone_id: target for drone_id, (_, _, target) in self.moves.items() if target is not None}

During the brief "hold" period after a move finishes animating but before the next turn starts, a drone that just landed in a real zone should visually merge into that zone's occupant wedge rather than float above it as a separate white circle — this dict is exactly the set of "who just arrived and should be drawn as part of the zone now", consulted by both draw_zones and draw_moving_drones below. on_update — the per-frame game loop

def on_update(self, dt: float) -> None:
    for key in self.keys_held:
        dx, dy = ARROWS[key]
        self.cam[0] += dx * PAN_SPEED * dt
        self.cam[1] += dy * PAN_SPEED * dt

    if self.paused or self.turn >= len(self.log):
        return

    if not self.moves and not self.holding:
        self.start_turn()
    self.timer += dt
    if not self.holding and self.timer >= MOVE_TIME:
        self.timer, self.holding = 0.0, True
    elif self.holding and self.timer >= HOLD_TIME:
        self.finish_turn()

Arcade calls this automatically every frame with dt, the elapsed time in seconds since the previous frame — using elapsed real time rather than a fixed frame count is what makes the animation speed independent of the machine's actual frame rate. Camera panning is applied first and unconditionally (even while paused, panning still works). Then: if paused, or every turn has already played, do nothing further. Otherwise this is a tiny explicit state machine with three states — idle (no active moves, not holding: start the next turn), animating (timer running up to MOVE_TIME, then flips into holding), and holding (pause for HOLD_TIME so a human eye can actually register the arrival, then call finish_turn() to advance).

Multi-path enabling, consolidated

You asked for this specifically, and it's genuinely spread across two files, so here is the single, consolidated answer:

  1. One PathFinder instance is reused for the whole fleet (§4, get_drones_paths): its zone_reservations and link_reservations tables persist and accumulate across every drone routed in the loop.
  2. Every drone's Dijkstra search happens over (zone, turn) states, not just zones, so "is this route free" is always asked with a specific turn attached — the same zone can be legal for drone 2 at turn 5 and illegal at turn 6, purely depending on what drone 1 already committed to.
  3. A winning route is permanently reserved the moment it's found (reserve_schedule), strictly first-come-first-served by drone ID — this is what forces later drones to route around earlier ones rather than the two interfering.
  4. The Simulator never re-plans — it independently re-verifies every move against live occupancy each turn (§6), so even if the offline reservation bookkeeping and the real turn-by-turn contention ever disagree slightly, no zone or connection can ever be physically over-filled at runtime; a drone that loses a contested slot just waits and retries.
  5. The net effect: distinct drones end up on genuinely different routes when the map offers a real fork (e.g. easy/02_simple_fork.txt's path_a/path_b), and on the same corridor staggered in time when it doesn't (drone 2 following drone 1 through a single-lane connection one or more turns behind) — both are the same mechanism, just with a different graph shape.
