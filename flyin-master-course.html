When you're ready, say something like "next phase" or "give me Phase 2" and I will produce that phase with the same level of depth — building directly on what you learned here, never repeating it, never jumping ahead into implementation.

Here is the contract for every phase in this course:

  • No code in early phases. Phases 1–3 are pure understanding: concepts, vocabulary, structure, reasoning.   • Every phase ends with a checkpoint. A short self-test so you know you're actually ready to move on, not just that you scrolled past it.
  • Every phase is scoped to "simplest correct solution." Per your goal, we deliberately avoid fancy algorithms, external graph libraries (they're forbidden anyway — more on that below), and over-engineered abstractions.   • Pure OOP, always. Every future phase will describe things as classes, attributes, and methods — because the subject requires a fully object-oriented design, and it will be tested live during your defense.
Why start with theory instead of architecture

Architecture is a set of answers. You can't evaluate whether an answer is good until you understand the question. Fly-In's real question is: "How do I move many agents through a shared, capacity-limited network at the same time, without collisions, in as few synchronized time-steps as possible?" That's a real field — Multi-Agent Path Finding (MAPF) combined with capacity-constrained flow over time. Once that question is crystal clear in your head, the architecture in Phase 3 will feel almost inevitable rather than arbitrary — every class will exist because you already know what job it needs to do.

Phase 1 begins here

Foundations & theory

Everything you must understand before you can meaningfully read an architecture diagram. No Python yet — only the mental models.

1.1 The mental model, in plain language

Strip away every technical term for a second. Fly-In is this: you are an air-traffic controller for a fleet of drones. There is a map made of parking spots ("zones") connected by corridors ("connections"). All your drones start crammed into one parking spot (the start hub) and must all reach a single destination parking spot (the end hub).

Time moves in discrete ticks called turns. On every turn, every drone simultaneously either moves to a neighboring spot or stays put. Some parking spots only fit one drone at a time. Some corridors only fit one drone at a time. Some spots are dangerous and take two ticks to cross. One spot type is closed entirely. Your job is to write a program that decides, turn by turn, where every drone goes — such that nobody ever collides or breaks a capacity rule, and the last drone arrives as early as possible.

Why this is harder than "just find the shortest path"

If you had exactly one drone, this would be a textbook shortest-path problem (Dijkstra/BFS) — pick the cheapest route and walk it. But you have many drones sharing a finite map at the same time. The moment two drones want the same limited resource (a zone slot or a connection slot) on the same turn, you have a scheduling conflict. Solving conflicts well — instead of drones endlessly waiting on each other — is the actual challenge of this project. That's the whole reason a "simulation / scheduling engine" exists as its own component, separate from "pathfinding."

These exact terms appear throughout the subject and will appear throughout every later phase. Get fluent in them now.

1.3 The input file format, exactly as specified

This is the ground truth from the subject (Chapter VI). Every later phase assumes you know this file format by heart.

nb_drones: 5
start_hub: hub 0 0 [color=green]
end_hub: goal 10 10 [color=yellow]
hub: roof1 3 4 [zone=restricted color=red]
hub: roof2 6 2 [zone=normal color=blue]
hub: corridorA 4 3 [zone=priority color=green max_drones=2]
hub: tunnelB 7 4 [zone=normal color=red]
hub: obstacleX 5 5 [zone=blocked color=gray]
connection: hub-roof1
connection: hub-corridorA
connection: roof1-roof2
connection: roof2-goal
connection: corridorA-tunnelB [max_link_capacity=2]
connection: tunnelB-goal
# a comment line — fully ignored

Line-by-line grammar, precisely:

  • Line 1 is always nb_drones: <positive_integer>. This must be able to handle any number of drones.
  • Zone lines start with one of three prefixes: start_hub:, end_hub:, or hub:, followed by <name> <x> <y> [metadata]. Coordinates are always integers.
  • Connection lines start with connection: followed by <name1>-<name2> [metadata]. Connections are always bidirectional.
  • Metadata is optional, wrapped in [...], space-separated key=value pairs, in any order.
  • Comments start with # and are ignored entirely.

Zone metadata keys and their defaults

KeyDefaultMeaning
zonenormalOne of normal, restricted, priority, blocked.
colornoneAny single-word string. Purely cosmetic — used later for the visualization layer.
max_drones1Maximum drones allowed in this zone at once. Ignored (unlimited) on start_hub and end_hub, even if written explicitly.

Connection metadata keys and their defaults

KeyDefaultMeaning
max_link_capacity1Maximum drones allowed to traverse this connection simultaneously.
Structural rules you must not violate when parsing
  • Exactly one start_hub and exactly one end_hub must exist.
  • Zone names must be unique; valid characters exclude dashes - and spaces (dashes are the connection separator, so a name containing one would be ambiguous).
  • A connection may only reference zones that were already defined earlier in the file.
  • a-b and b-a are the same connection — defining both is a duplicate error, not two edges.
  • Zone zone= values outside {normal, blocked, restricted, priority} are a parsing error.
  • max_drones and max_link_capacity must be positive integers when present.
  • Any other malformed line must stop the program with a clear message naming the offending line and the reason.

Phase 4 will turn each of these bullet points into one parser responsibility. For now, just recognise that every one of these rules is a future unit test.

1.4 Zone types & movement cost

Each zone has exactly one type, and the type determines how many turns it costs to move into that zone (cost is about the destination, not the origin):

TypeCost to enterBehavior
normal1 turnDefault. No special behavior.
priority1 turnSame cost as normal, but your pathfinding should prefer it when a choice exists — think of it as a "fast lane" the algorithm should favor.
restricted2 turnsA drone that starts moving toward it is committed: it must arrive exactly on the next turn after that — it cannot idle mid-corridor waiting for space. See §1.7.
blocked—Never enterable. A path that requires stepping into a blocked zone is simply invalid and must never be produced by your algorithm.
Why "priority" matters even though its cost equals "normal"

This is a subtle but important detail: priority zones do not get a numeric discount. They are a routing hint, not a cost hack. Your pathfinding heuristic should be built so that, all else being equal, a route touching more priority zones is chosen over one that doesn't. We'll return to exactly how to encode "prefer, don't require" in Phase 6 — for now, just store this fact: priority affects choice, not arithmetic.

1.5 Two independent capacity systems

There are two separate resources that can run out, and beginners often conflate them. Keep them mentally separate — you will model them as two separate counters later.

1. Zone capacity — "how many drones can be parked here"

  • Default is 1 drone per zone at a time.
  • Overridable per-zone via max_drones=N.
  • The start hub and end hub are always unlimited, regardless of any max_drones written on them (it's ignored, not an error).

2. Connection capacity — "how many drones can be mid-transit on this corridor at once"

  • Default is 1 simultaneous traversal.
  • Overridable via max_link_capacity=N on the connection line.
Pitfall — the "free up space this same turn" rule

The subject is explicit: drones moving out of a zone free up capacity for that same turn, and a destination zone must have available space after all drones leaving it have been accounted for. In other words, capacity isn't checked against a frozen snapshot of "who's there right now" — it's checked against "who will still be there after everyone's simultaneous move for this turn resolves." This single sentence in the subject is the difference between a simulation that deadlocks unnecessarily and one that doesn't. It will directly shape how the scheduling engine evaluates a turn in Phase 7 (in short: compute departures before arrivals).

1.6 Turns & simultaneous movement

On every simulation turn, each still-active drone does exactly one of three things:

  1. Move into an adjacent normal or priority zone (1-turn move), if capacity allows.
  2. Begin (or continue) a 2-turn move into an adjacent restricted zone (see §1.7).
  3. Stay in place — a deliberate, valid choice, e.g. to wait for capacity to free up.

The simulation stops the moment every drone has reached the end hub. The score is simply the number of turns that took — fewer is strictly better. That's it: this one number is what a peer-evaluator (and the automated benchmarks) will compare you on.

1.7 The restricted-zone commitment rule (read this twice)

This is the single trickiest mechanic in the whole subject, and it is exactly the kind of thing an evaluator will probe you on. Read the subject's own wording carefully:

Verbatim rule, restated precisely

Moving toward a restricted zone costs 2 turns. Once a drone starts that move, it is committed: it must arrive at the destination on the very next turn after departure (i.e., exactly 2 turns after it left its previous zone). It cannot pause mid-corridor waiting for the destination zone to have free capacity. It cannot cancel and turn back either — the only outcome of starting that move is arriving on schedule.

The practical consequence: before you ever let a drone begin a move toward a restricted zone, you must already know — with certainty — that the destination zone will have a free slot on the turn the drone is due to arrive. If you can't guarantee that, the drone must not depart yet; it should wait one more turn in its current zone instead.

Why this rule exists in the design (not just as flavor text)

It forces your scheduler to reason about the future, not just the present turn. This is exactly why "just run Dijkstra and walk the path" is insufficient — you need a scheduler that reserves the destination slot in advance for multi-turn moves. This single rule is the strongest hint the subject gives you that a time-aware data structure (tracking "who/what occupies which resource on which future turn") is the right tool. We'll formalize that idea in §1.9 and use it for real in Phase 7.

1.8 Graph theory crash course (only what you need)

You said you're a Python beginner with no background here — so no jargon without a plain-English translation first.

What a graph is

A graph is just a collection of nodes (dots) and edges (lines connecting pairs of dots). That's the entire idea. In Fly-In: nodes = zones, edges = connections.

Vocabulary you'll actually use

TermPlain meaningIn Fly-In
Node / vertexA dotA Zone
EdgeA line connecting two dotsA Connection
Undirected graphEdges have no arrow — you can cross them either wayAll connections are bidirectional (explicitly stated in the subject)
Weighted graphEach edge/node has a "cost" to useMovement cost depends on the destination zone's type (1 or 2 turns)
Adjacency"Which nodes are directly connected to this one"What you check to know a drone's legal next moves
PathA sequence of edges linking a start node to a target nodeA drone's route from start_hub to end_hub
DegreeHow many edges touch a nodeHow many neighbouring zones a zone has

How to store a graph in memory (conceptually)

There are two classic representations. You don't need to pick one right now — Phase 3 will make the choice explicit — but you should recognise both by name:

  • Adjacency list: each node keeps a small list/collection of the nodes it directly connects to. Simple, memory-efficient, and the natural fit for a sparse map like this one (most zones connect to only a handful of neighbours, not to everything).
  • Adjacency matrix: a big 2D grid where cell [i][j] says whether node i connects to node j. Wastes memory on sparse graphs — not the right tool here.
Why this matters for "simplest solution"

Fly-In maps are sparse (a handful of neighbours per zone, not "everyone connects to everyone"). An adjacency list, implemented as each Zone simply holding a small collection of its own Connection objects, is both the simplest and the most efficient choice here. This is a preview of a real decision you'll make in Phase 3/5 — no need to act on it yet, just recognise the reasoning style: pick the option that is simple and fits the data shape, not the fanciest one available.

Shortest path, briefly

For a single agent with no other constraints, finding the cheapest route between two nodes is a solved, classic problem:

  • BFS (Breadth-First Search) — finds the shortest path by number of edges, assuming every edge costs the same. Simple to reason about: explore neighbours layer by layer, like ripples in a pond.
  • Dijkstra's algorithm — the generalisation of BFS for edges/nodes with different costs (which is our case, since restricted zones cost 2 and everything else costs 1). It always expands the cheapest-so-far node next, using a priority queue.

Since our "weight" lives on nodes (the destination zone's type) rather than on edges, you'll mentally translate "zone cost" into "cost of the edge leading into that zone" — a completely standard and simple trick. This is genuinely all the pathfinding theory Fly-In's mandatory part requires; there is no need for A*, or anything more exotic, to satisfy the subject. Simpler is not just acceptable here — it is the intended solution.

1.9 Why this is (a simplified) Multi-Agent Path Finding problem

Once you have more than one drone sharing a capacity-limited map at the same time, you leave "shortest path" territory and enter a well-known field called Multi-Agent Path Finding (MAPF). You don't need to become a MAPF researcher — you need exactly three ideas from it:

Idea 1 — Time-expanded thinking

Instead of asking "is zone X occupied?", the useful question is always "is zone X occupied on turn T?" Mentally, picture not one map, but a stack of identical maps, one per future turn — this is called a time-expanded graph in the literature. A zone's capacity is really a capacity per time-slot, not a single global capacity. You don't need to build this as a literal giant data structure (that would be over-engineering for this project's scale) — but thinking in these terms is what makes the restricted-zone commitment rule (§1.7) and the "free up space this same turn" rule (§1.5) make sense together, instead of feeling like two unrelated special cases.

Idea 2 — Reservations prevent conflicts before they happen

The simplest robust technique used in real MAPF-lite systems: when you commit a drone to a move, you reserve the destination resource (zone slot or connection slot) for the turn(s) it will be occupied. Any other drone's plan that would need that same reserved slot on that same turn is rejected or delayed. This turns "avoid collisions" from a reactive cleanup problem into a proactive bookkeeping problem — which is far easier to implement correctly and explain in a defense.

Idea 3 — You don't need optimal, you need good and explainable

True optimal MAPF solving is computationally very expensive (NP-hard in general) and is absolute overkill for this project's scoring system, which just compares total turn counts against reasonably generous benchmarks (see the "Easy/Medium/Hard" targets in the subject). A simple, well-reasoned greedy strategy — "give each drone its cheapest known valid path, let drones move whenever their next step is free, make blocked drones wait, prefer priority zones when routes tie" — is entirely sufficient to hit every mandatory requirement and even most of the benchmark targets. This is the strategy we will formalize (still without code) in Phase 6.

Putting it together — the two-layer mental split

Keep this split in your head permanently, because it will become two of your future modules:

  • Pathfinding layer — "if I ignore every other drone, what is the cheapest legal route for this one drone, and which route should be preferred when several are equally cheap (favor priority zones)?"
  • Scheduling/simulation layer — "given everyone's preferred route, resolve turn-by-turn who actually gets to move this turn, who has to wait, and who is mid-flight through a restricted zone."

1.12 OOP mental preview (names only, no implementation)

You explicitly do not want implementation yet — good instinct. But it will help you read Phase 3 much faster if these five ideas already have a "home" in your head as concepts, not yet as code:

  • Something that represents a Zone — a single place on the map, aware of its own name, position, type, and current occupants.
  • Something that represents a Connection — a corridor between two zones, aware of its own capacity and current traffic.
  • Something that represents a Drone — a single agent, aware of its own identity, current position, and destination.
  • Something that owns the whole network — holds all zones and connections together and can answer "who is adjacent to whom."
  • Something that reads the input file and produces validated zones/connections/drone-count from raw text — and rejects anything malformed with a clear message.
  • Something that runs the simulation turn by turn — decides moves, resolves conflicts, and produces the turn log.
  • Something that shows the result to a human — colored terminal output and/or a simple graphical view.

That's it — seven ideas, seven future classes (roughly). Phase 3 will name them properly, define exactly what each one is responsible for (and, just as importantly, what it is not responsible for), and show how they hand data to each other. Nothing here is binding yet; treat it as a set of labelled boxes you'll fill in soon.

1.13 Comprehension check — don't skip this

Answer each one honestly in your head before expanding it. If more than one or two feel shaky, re-read the relevant section above before moving to Phase 2.

What's the difference between a zone's capacity and a connection's capacity?
Zone capacity (max_drones, default 1) limits how many drones can be physically present inside a zone at once. Connection capacity (max_link_capacity, default 1) limits how many drones can be traversing a given corridor at the same time. They are tracked and enforced independently.
Why can't a drone "pause" halfway through a move into a restricted zone?
Because the subject defines that move as an atomic 2-turn commitment: once started, the drone must arrive exactly on the next turn. There is no valid state of "waiting on the connection." This means your scheduler must verify the destination will be free before allowing the drone to depart — not react after the fact.
Does a "priority" zone cost less than a "normal" zone?
No — both cost 1 turn to enter. "Priority" is a preference signal for your pathfinding/tie-breaking logic, not a discount. A "blocked" zone can never be entered, and a "restricted" zone always costs 2 turns.
Why is plain Dijkstra, run once per drone independently, not sufficient by itself?
Because Dijkstra only guarantees the cheapest route for a single agent in isolation — it knows nothing about other drones competing for the same zone/connection slots on the same turn. You still need it (each drone needs *a* good candidate route), but a separate scheduling/simulation layer must resolve real-time conflicts between drones' plans.
What exactly does "drones moving out of a zone free up capacity for that same turn" mean in practice?
When evaluating whether a zone has room for an incoming drone this turn, you must first account for every drone that is simultaneously leaving that zone this same turn. So capacity checks should be evaluated as "departures processed, then arrivals checked" rather than against a stale occupancy count from the start of the turn.
Name the two things forbidden by the "Constraints" chapter that most directly affect how you'll write the Graph and pathfinding code.
1) No external graph libraries (networkx, graphlib, etc.) — you build your own adjacency-list graph and your own BFS/Dijkstra. 2) The project must be fully object-oriented — no bag-of-functions script; every concept becomes a class with clear responsibilities.
In one sentence, what does your program's score depend on?
The total number of simulation turns needed for every drone to go from the start hub to the end hub while respecting all movement, occupancy, and capacity rules — fewer turns is better.
